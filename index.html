Lab 2: Read-only Kubernetes troubleshooting assistant

Problem: A pod is in CrashLoopBackOff and you must read events, logs and describe output to find the cause.

Architecture: kubectl (read-only) → collect describe/events/logs → redact → LLM → plain-language cause + suggested fix → human decides.

Tools: kubectl, a read-only ServiceAccount, Python 3, an LLM API key in a vault.

Steps

  1. Create a read-only role: 
    kubectl create serviceaccount ai-triage -n demo
kubectl create role ai-triage-ro -n demo --verb=get,list --resource=pods,pods/log,events
kubectl create rolebinding ai-triage-ro -n demo --role=ai-triage-ro --serviceaccount=demo:ai-triage
  2. Collect context: 
    POD=$1; NS=demo
{ kubectl -n $NS describe pod $POD | tail -n 60
  kubectl -n $NS get events --field-selector involvedObject.name=$POD | tail -n 20
  kubectl -n $NS logs $POD --previous --tail=100; } > /tmp/ctx.txt
  3. Redact and send to the LLM (as in Lab 1): ask for "root cause, evidence lines, one fix, say unsure if unclear".
  4. Print the answer. Do not let the script run kubectl apply/delete.

Expected output: "OOMKilled: container limit 256Mi; evidence: Reason: OOMKilled; fix: raise memory limit or fix leak."

Security: read-only RBAC, namespace-scoped, redact env vars and tokens, never send Secrets, log every request.

Business value: faster first diagnosis for on-call; step toward approved auto-remediation.

10. Practical Hands-on Lab of the Day
Lab 1: AI analysis of Jenkins pipeline failures (read-only)

Problem: Developers spend time reading long Jenkins console logs to find why a build failed.

Architecture

Jenkins job fails → post-build step grabs last 300 log lines
        → script sends log to an LLM API → summary + likely cause
        → posted as a comment / Slack message (no write access to Jenkins/infra)

Tools: Jenkins, Python 3, an LLM API key (stored in Jenkins credentials / vault), requests.

Steps

  1. In Jenkins, add a credential LLM_API_KEY (secret text).
  2. Add to your Jenkinsfile:
post {
  failure {
    withCredentials([string(credentialsId: 'LLM_API_KEY', variable: 'LLM_API_KEY')]) {
      sh '''
        tail -n 300 "$WORKSPACE/build.log" > /tmp/tail.log || true
        python3 ai_triage.py /tmp/tail.log
      '''
    }
  }
}

(Make the build write to build.log, e.g. tee build.log, or fetch via currentBuild.rawBuild.getLog(300) in a shared library.)

  1. ai_triage.py (outline, adjust endpoint/model to your provider's docs):
import os, re, sys, requests
log = open(sys.argv[1]).read()
# redact obvious secrets before sending
log = re.sub(r'(?i)(password|token|secret|key)\s*[=:]\s*\S+', r'\1=<redacted>', log)
prompt = ("You are a CI triage assistant. Given this Jenkins log tail, "
          "give: 1) most likely root cause, 2) the exact failing step, "
          "3) one suggested fix. Say 'unsure' if not clear.\n\n" + log)
r = requests.post(os.environ["LLM_URL"],
    headers={"x-api-key": os.environ["LLM_API_KEY"]},
    json={"model": os.environ["LLM_MODEL"], "max_tokens": 500,
          "messages": [{"role": "user", "content": prompt}]}, timeout=60)
print(r.json())
  1. Send the printed summary to Slack/MR comment with a webhook.

Expected output: a 5-line message such as "Cause: docker pull timed out at registry; step: Build image; fix: retry / check registry network."

Security

  • Redact secrets before sending; never send full logs with credentials.
  • Read-only: the AI suggests, humans act.
  • Check your data-handling policy: logs leave your network.

h) Beginner lesson: index funds and SIP

An index fund buys all shares in an index such as Nifty 50, so you own a small slice of 50 big companies without picking any. A SIP (systematic investment plan) invests a fixed amount every month, for example Rs 1,000, whatever the market does. When prices fall you get more units; when they rise you get fewer, so your average cost smooths out. Benefits: low cost, no need to guess the top or bottom, builds a habit. Limits: the fund still falls when the market falls, and returns are never guaranteed. Try it: write down what Rs 1,000 a month for 12 months would have bought at three different Nifty levels. h) Beginner lesson: support and resistance

Support is a price zone where a falling stock often stops falling because buyers step in. Resistance is a zone where a rising stock often stalls because sellers appear. h) Beginner lesson: what is a stop loss?

A stop loss is an order you place in advance to sell a stock automatically if its price falls to a level you choose. It limits how much one wrong decision can cost. Example: you buy at Rs 100 and set a stop at Rs 92. If the price drops to Rs 92, your broker sells, and your loss is about 8% instead of whatever the fall becomes. Choose the level before buying, using a reason such as a recent low, not a random number. Warning: in fast or thinly traded stocks the sale can happen below your stop price (called slippage), and a price can touch your stop for a moment and then recover. Wider stops need smaller position sizes, which links to the previous lesson on position sizing. Try it: pick a stock you follow, write the buy price, a stop 8% lower, and the rupee loss on Rs 5,000 invested (Rs 400). Education only; no guarantees; consult a SEBI-registered adviser.

h) Beginner lesson: position sizing (how much to put in one stock)

Position sizing means deciding how much money goes into one idea before you buy. It protects you when you are wrong, and everyone is wrong sometimes. A common rule of thumb is that no single stock should be more than about 5 to 10% of your investing money, and a risky small cap much less. Example: you have Rs 1,00,000 to invest. A 5% position is Rs 5,000. If that stock falls 40%, you lose Rs 2,000, which is 2% of your total: painful but survivable. Had you put in Rs 50,000, the same fall costs Rs 20,000. Buying in parts (say three purchases over weeks) also stops one bad day from setting your whole price. Pair this with diversification: spread across sectors and keep most money in a broad index fund or SIP. Before buying, write down the reason that would make you sell. Try it: pick a stock you follow, size a 5% position for a Rs 1,00,000 portfolio, and compute the loss if it falls 30%. Education only; no guarantees; consult a SEBI-registered adviser.

h) Beginner lesson of the day: what are EPS and the P/E ratio?

EPS (earnings per share) is the company's profit divided by the number of shares. If a company earns ₹1,000 crore and has 100 crore shares, EPS is ₹10. It tells you how much profit belongs to one share.

P/E (price-to-earnings ratio) is the share price divided by EPS. If the price is ₹200 and EPS is ₹10, P/E is 20. In plain words, you pay ₹20 for every ₹1 of yearly profit. A higher P/E means investors expect faster growth (or the stock is expensive); a lower P/E means slower growth (or the stock is out of favour).

How to use it: a P/E number means little alone. Compare it with (1) the same company's own past P/E, and (2) similar companies in the same sector: IT with IT, banks with banks. Banks are often judged with other measures too, such as price to book value.

Limits: if a company makes a loss, EPS is negative and P/E has no meaning (the case for Tata Motors PV this quarter). One-time gains can make P/E look low. P/E uses past profit, but share prices move on future expectations.

Try it today: on screener.in, open SBI and ITC, write down each P/E, and compare with the sector average shown there. Then write one line: "cheap or expensive versus peers, and why might that be?"

2. Two classes of the day

Class 1: Docker in production (images, security, multi-stage)

Objective: build small, reproducible, non-root images, run them with limits, and keep a Docker host from dying of disk, memory or log growth.

Theory. An image is a stack of read-only layers plus metadata; a container adds a thin writable layer and runs one process inside namespaces (what it can see) and cgroups (what it can use). Three production rules follow. (1) Small and reproducible: use a multi-stage build so compilers and caches stay in the build stage; copy only the artifact into a minimal runtime image (distroless, alpine or a slim base). Pin the base by version, ideally by digest, and order the Dockerfile from least to most frequently changing (dependency manifests before source) so the build cache works. (2) Least privilege: USER a non-root uid, drop all capabilities and add back only what is needed, --read-only root filesystem with a tmpfs for scratch, no-new-privileges, never mount /var/run/docker.sock into app containers (it is root on the host). (3) Bounded resources: without -m a container may consume all host memory; without a log rotation setting the default json-file driver keeps logs forever, which is the most common cause of a full disk on a Docker host.

Things that bite: a shell-form ENTRYPOINT makes /bin/sh PID 1 so SIGTERM never reaches your app and every deploy waits 10 seconds then kills it; latest tags make rollbacks impossible; secrets passed with ARG or ENV are visible in docker history (use BuildKit --mount=type=secret); COPY . . without a .dockerignore ships your .git and .env into the image.

Dockerfile (multi-stage)              Registry                 Runtime host
 stage build: JDK + Maven  --\
   COPY pom.xml ; mvn dep       \  artifact only
   COPY src ; mvn package        +--> stage run: distroless JRE   --push--> app:1.4.2 + digest
 stage run : USER 10001, jar         non-root, no shell, ~150 MB           |
                                                                          v
                         scan (Trivy) + SBOM in CI  -->  docker run --read-only --cap-drop ALL -m 512m

In real companies: a platform team owns approved base images that are rebuilt weekly and scanned; CI builds with BuildKit and layer cache from the registry, tags with the git SHA, scans and fails on critical CVEs with a fix available, signs the image, and deploys by digest. Hosts (or nodes) run docker system prune-style cleanup only through a scheduled, reviewed job, and logs go to a collector with rotation as a safety net.

Class 2: Kubernetes in production (requests/limits, HPA, PDB, upgrades)

Objective: size workloads correctly, scale them automatically, keep them available during node drains and upgrades, and upgrade a cluster without surprises.

Theory. Requests are what the scheduler reserves; limits are what the kubelet enforces. A memory limit hit means OOM kill; a CPU limit hit means throttling (latency, not death). Requests and limits also set the QoS class: Guaranteed (requests equal limits for all containers), Burstable, BestEffort; under node pressure BestEffort pods are evicted first. A common senior practice: set memory request equal to memory limit (no surprise eviction), set a CPU request that matches steady usage, and be careful with CPU limits on latency-sensitive services (many teams drop them and rely on requests and node sizing). Use the Vertical Pod Autoscaler in recommendation mode to find real numbers.

HPA computes desired = ceil(current * currentMetric / targetMetric) against metrics-server (CPU, memory) or custom metrics. It uses CPU as a percentage of the request, so wrong requests mean wrong scaling. It needs readiness probes to be honest (new pods take traffic only when ready) and behavior.scaleDown.stabilizationWindowSeconds to avoid flapping. PDB (PodDisruptionBudget) limits voluntary disruptions such as kubectl drain, node upgrades and autoscaler scale-down: minAvailable: 2 or maxUnavailable: 1. A PDB with minAvailable equal to replicas blocks every drain forever, and it does not protect against crashes or node failure. Pair it with topology spread constraints so replicas sit in different zones and nodes.

Upgrades. Kubernetes ships minor releases a few times a year and supports each for a limited window, so upgrading is a routine job, not a project. Rules: upgrade one minor version at a time; control plane first, then nodes (kubelet may lag the API server within the documented skew); read the release notes and deprecation guide; scan manifests for removed APIs before upgrading (tools such as kubent or pluto, or the API server's apiserver_requested_deprecated_apis metric); upgrade a staging cluster first; on managed services (EKS, AKS, GKE) the provider upgrades the control plane and you roll node groups. Rolling nodes means cordon, drain (respecting PDBs), replace, and verify, one node pool at a time with surge capacity.

 requests/limits --> QoS class --> who is evicted first (BestEffort > Burstable > Guaranteed)
 metrics-server --> HPA (ceil(cur*metric/target)) --> Deployment replicas --> scheduler (needs free requests)
 node upgrade: cordon --> drain (PDB gate) --> new node joins --> pods reschedule --> verify --> next node

resources:
  requests: { cpu: "250m", memory: "512Mi" }
  limits:   { memory: "512Mi" }          # memory request == limit; CPU limit deliberately omitted
---

metadata: { name: web }

  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: web }
  minReplicas: 3
  maxReplicas: 12
  metrics: [{ type: Resource, resource: { name: cpu, target: { type: Utilization, averageUtilization: 65 } } }]
  behavior: { scaleDown: { stabilizationWindowSeconds: 300 } }
---
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: web }
spec: { maxUnavailable: 1, selector: { matchLabels: { app: web } } }

Quarterly upgrade windows, a staging cluster that always runs one version ahead, and a pre-upgrade API deprecation check in CI are normal.

Show solution

Investigation. 1) docker system df shows images 88 GB (71 GB reclaimable), build cache 18.7 GB, volumes 14 GB, and containers 61.9 GB, which is unusually large for 14 containers. Containers' size includes writable layers and the logs sit in /var/lib/docker/containers/<id>/<id>-json.log. The 55 GB log belongs to report-gen, which prints a line per record at DEBUG level; the default json-file driver has no rotation. 2) Safest first: free log space without restarting by truncating the file in place: truncate -s 0 /var/lib/docker/containers/b27c.../b27c...-json.log (deleting the file would not free space while the process holds it open). That instantly gives 55 GB. Then reclaim cache and dangling data: docker builder prune --filter until=72h, docker image prune -a --filter "until=168h" (only unused images; the 9 active ones are untouched). Do not run docker volume prune blindly: named volumes may hold registry mirror data; list with docker volume ls -f dangling=true and check each. 3) Prevent: set /etc/docker/daemon.json with "log-driver":"json-file","log-opts":{"max-size":"10m","max-file":"3"} (applies to newly created containers, so recreate report-gen in a quiet window), fix the debug logging, add a disk alert on predicted fill time (predict_linux style, see AIOps below), and schedule a reviewed weekly builder prune.

Root cause. No log rotation on the Docker host plus DEBUG logging left on in production; a secondary factor was 80% unused images and 18 GB of stale build cache with no cleanup job.

Fix. Immediate: truncate the one huge log, prune build cache and old unused images (about 90 GB freed), restart the 07:00 build. Permanent: daemon-level log rotation, recreated container, cleanup job, and a disk-fill-in-24h alert.

4. Interview practice (Docker)

Q1. Your team's Docker image is 1.4 GB and takes 12 minutes to build and push. What would you do?

Show answer

1) Measure first: docker history --no-trunc (or dive) to see which layers are big and which rebuild every time. 2) Convert to a multi-stage build so compilers, package caches and test tools do not ship; pick a slim or distroless runtime base. 3) Reorder the Dockerfile: copy dependency manifests and install first, copy source last, so the dependency layer is cached. 4) Add a .dockerignore (.git, node_modules, test data). 5) In CI use BuildKit with a registry cache (--cache-from/--cache-to) because CI runners start with an empty cache. 6) Chain cleanup in the same RUN (apt-get install ... && rm -rf /var/lib/apt/lists/*), otherwise the deleted files still live in the earlier layer. 7) Report the result: size, build time, pull time on a new node. What the interviewer is checking: that you measure before optimising and understand layers, cache order and CI cache behaviour.

Q2. A container keeps restarting with exit code 137, but the app works locally. How do you investigate?

Show answer

137 = 128 + 9, SIGKILL. Two common sources: the kernel OOM killer (memory limit too low) or an orchestrator kill after a failed graceful stop. Steps: docker inspect <c> --format '{{.State.OOMKilled}} {{.State.ExitCode}}'; if OOMKilled is true compare docker stats with the -m limit and check dmesg -T | grep -i oom on the host. Locally there is usually no limit, so the problem hid. Fix by finding the real memory need (heap flags such as MaxRAMPercentage for Java, worker counts for Node or Python) and set a limit with headroom, not simply doubling it. If OOMKilled is false, check whether the app ignores SIGTERM (shell-form ENTRYPOINT, PID 1 problem) and gets killed after the stop timeout; use exec form or --init. What the interviewer is checking: exit-code literacy, difference between OOM and failed stop, and that you do not fix by raising limits blindly.

Q3. Security asks you to prove that production containers are not running as root and have no known critical vulnerabilities. What do you set up?

Show answer

Prevent and detect. Build time: USER non-root in the Dockerfile, minimal base image, Trivy or Grype scan in CI that fails on critical vulnerabilities with a fix available, SBOM generated and stored with the image, image signed (cosign). Registry: only approved registries and tags by digest; continuous re-scan because new CVEs appear after build. Runtime (Kubernetes): enforce with Pod Security Admission or a policy engine (runAsNonRoot: true, allowPrivilegeEscalation: false, drop capabilities, read-only root filesystem), so a root container is rejected at admission. Evidence: the CI scan reports, the admission policy and a weekly report of images by age and finding count. Handle exceptions with an expiry date. What the interviewer is checking: layered thinking (build, registry, admission, runtime) and evidence for auditors, not a single scanner.

6. AIOps: predictive infrastructure monitoring

How AI helps. Classic alerts fire when a threshold is crossed; predictive monitoring forecasts when it will be crossed, so you act during working hours. Examples: disk fill-time, certificate expiry, memory leak slope, queue growth, capacity for the next sale. The simplest tool is not a model at all: Prometheus predict_linear fits a straight line to recent samples. 8. Career: leadership skills expected per level

Lesson. At two years you are measured on your output: tickets closed, pipelines fixed, incidents handled. Leadership at this level is small and concrete: you own a task end to end, you tell people early when you are blocked, and you leave things better documented than you found them. At the senior level leadership becomes multiplying others. You review pull requests so that the team learns, not only so that code merges. Prometheus and Grafana: histograms, p99 and recording rules

What it is: Prometheus stores time series; a histogram metric exposes request durations as cumulative buckets, from which you compute percentiles. Why it matters: averages hide pain; p99 is what slow users feel, and it is the usual latency SLI. How it works:

http_request_duration_seconds_bucket{le="0.1"|"0.5"|"1"|"+Inf"}   (counters)
p99 = histogram_quantile(0.99, sum by (le) (rate(http_request_duration_seconds_bucket[5m])))

Sum by le across instances before taking the quantile (never average per-pod quantiles). Bucket boundaries decide accuracy, so put buckets around your SLO threshold. Save expensive expressions as recording rules so dashboards and alerts stay fast, and keep label cardinality low (no user IDs). In Grafana use one variable for service and link panels to runbooks. Percentiles cannot be averaged. Summing the bucket counters across pods gives the combined distribution, from which the quantile is computed correctly. An average of per-pod p99 values can be far from the real overall p99.

10. AI pro: tool use design (schemas, errors, idempotency)

Concepts. In tool use (function calling) the model does not run anything: it emits a structured request naming a tool and arguments; your code executes it and returns a result; the model continues. The tool's name, description and JSON Schema are the only interface the model sees, so they are product design, not plumbing. Good tools are few, narrow and named for outcomes (get_deployment_status, restart_pod), not thin wrappers over a raw shell or an entire API.

Design pattern. (1) Schemas: closed argument sets, enums instead of free strings, required fields, bounds, additionalProperties: false; describe when to use the tool and when not to. (2) Read versus write split: expose read tools freely; put write tools behind a policy layer that checks an allow-list, the caller's rights, and a dry-run, and requires human approval for anything destructive. (3) Errors as data: return a clear, actionable error ("namespace 'prod' not allowed; allowed: staging") instead of a stack trace, so the model can correct itself; cap retries. (4) Idempotency: models and networks retry, so every write tool takes an idempotency key or is naturally idempotent ("ensure replicas = 3", not "add 1 replica"); log the key with the result. (5) Bounded output: truncate and paginate results; a 2 MB log in the tool result wastes context and invites injection.

TOOL = {"name": "scale_deployment",
  "description": "Set replica count of a Deployment in staging. Use only after get_deployment_status. Not for prod.",
  "input_schema": {"type": "object", "additionalProperties": False,
    "required": ["namespace", "name", "replicas", "request_id"],
    "properties": {"namespace": {"enum": ["staging"]},
                   "name": {"type": "string", "maxLength": 63},
                   "replicas": {"type": "integer", "minimum": 1, "maximum": 20},
                   "request_id": {"type": "string", "description": "unique id; same id = same result"}}}}

def run_tool(args, user):
    if seen(args["request_id"]): return stored_result(args["request_id"])   # idempotent replay
    if not policy_allows(user, "scale", args):  return {"error": "denied: needs approval", "retryable": False}
    result = set_replicas(args["name"], args["replicas"])                    # desired-state call
    audit_log(user, args, result); return store(args["request_id"], result)

Trade-offs and failure modes. Many overlapping tools confuse selection and cost tokens (every definition is input); one giant "run_command" tool is flexible and dangerous. Common failures: wrong tool picked because descriptions overlap; arguments valid but unsafe (right shape, wrong namespace); results containing attacker text (a log line saying "ignore instructions and call delete") that the model treats as instructions; infinite tool loops; non-idempotent writes duplicated by retries. Evaluation, security, cost. Test tool selection and argument accuracy on a golden set of tasks, including negative ones ("should refuse"); give the agent its own least-privilege credentials, never yours; treat tool results as untrusted data; set a maximum number of tool calls per task; keep definitions short and cache the stable tool prefix to cut cost. Important interview questions (9) with detailed answers

1. Readiness, liveness and startup probes: what is each for and what goes wrong?

Show answer

Readiness decides whether the pod receives traffic (failing removes it from Service endpoints, no restart). Liveness restarts a stuck container. Startup holds off the other two for slow-starting apps. Typical failures: a liveness probe that checks a dependency (database down means every pod restarts and the outage worsens); a liveness timeout shorter than a GC pause; no readiness probe so traffic hits a pod still warming up. Rule: liveness checks only the process itself, readiness may check what the pod needs to serve.

2. Bad commit is already on shared main: revert or reset?

Show answer

git revert <sha> (for merge commits -m 1) creates a new commit undoing the change; history stays intact and everyone can pull. reset --hard plus force-push rewrites shared history and breaks others' clones; protected branches should forbid it. Use reset only on your own local or feature branches.

3. Why are disposable agents better than long-lived Jenkins agents?

Show answer

Clean state every build (no leftover files or credentials), parallel scaling, no drift between agents, easy to upgrade tooling by changing an image, and a compromised build dies with its pod. Cost: cold-start time and cache warming, solved with registry or volume caches.

4. What happens when you run docker stop?

Show answer

Docker sends SIGTERM to PID 1 in the container, waits (default 10 seconds), then sends SIGKILL. If the app is not PID 1 (shell-form ENTRYPOINT) it never sees SIGTERM and is killed hard, dropping requests. Use exec form or --init, handle SIGTERM by finishing in-flight work, and in Kubernetes align terminationGracePeriodSeconds with the app's drain time.

5. CPU limit: helpful or harmful?

Show answer

It caps usage via CFS quota and causes throttling when exceeded even if the node is idle, adding latency spikes in bursty services. Benefits: protects neighbours and keeps cost predictable. Many teams set CPU requests accurately and omit limits for latency-sensitive services; they keep limits for batch or untrusted workloads. Check container_cpu_cfs_throttled_periods_total before deciding.

6. A rollout is stuck with new pods not becoming ready. What do you check, and what does Kubernetes do?

Show answer

kubectl rollout status, describe on the new pods (events: image pull, probe failures, insufficient resources), logs of the new pods. The Deployment honours maxUnavailable and maxSurge, so old pods keep serving while new ones fail; after progressDeadlineSeconds the rollout is marked failed but not rolled back automatically. Fix forward or kubectl rollout undo; a GitOps tool should revert the Git commit instead.

7. Why OIDC instead of access keys in CI?

Show answer

The CI provider issues a short-lived signed token per job; the cloud trusts it through a role whose trust policy checks the repo, branch or environment claims, and returns temporary credentials. No long-lived secret to leak or rotate, and permissions are tied to which pipeline is running. Keep the permission id-token: write to the job that needs it.

8. Load average is 20 on 4 CPUs but CPU is 90% idle. Explain.

Show answer

Load counts runnable tasks and tasks in uninterruptible I/O wait (D state). High load with idle CPU means tasks are blocked on disk or network storage. Check vmstat 1 (wa, b columns), iostat -x, ps -eo stat,cmd | grep '^D', and NFS or EBS latency.

9. Rebase or merge for feature branches?

Show answer

Rebase your private branch onto main for a linear, clean history before the PR; merge (or squash merge) into main through the PR. Never rebase a branch others have based work on. Pick one policy per repo, enforce it in branch protection (for example squash-only), and document it. Interviewers want a reasoned team policy, not a religion.

Two troubleshooting exercises

Exercise 1. After a successful pipeline, pods show ImagePullBackOff in the new namespace; describe says "pull access denied" for registry.internal/app:1.4.2. The same image runs in the old namespace.

Show solution

Likely the new namespace lacks the image pull secret. Check kubectl get secret -n new and the pod's imagePullSecrets; pull secrets are namespaced. Confirm with kubectl describe pod events (the exact registry message), then verify the tag exists (crane ls or the registry UI) in case of a typo. Fix: create the secret in the namespace (from your secret store, never from chat) and reference it in the pod spec or attach it to the namespace's default ServiceAccount; for cloud registries prefer node or workload identity so no secret is needed. Prevention: namespace bootstrap automation (Helm chart or Kustomize base) that always creates the pull secret, and a CI smoke test that deploys to a fresh namespace. Success: new pods Running within a minute, kubectl get events clean.

Exercise 2. Black Friday load test: the HPA scaled from 3 to 12 replicas but 6 pods stay Pending with "0/5 nodes are available: 5 Insufficient cpu". Response times are poor.

Show solution

kubectl describe pod confirms scheduling failure by requests, not real usage. kubectl describe node | grep -A8 "Allocated resources" shows nodes fully reserved. Steps: immediate, add node capacity (resize the node group or enable cluster autoscaler so Pending pods trigger new nodes), and temporarily reduce over-large requests if monitoring shows pods use far less (check with VPA recommendations). Root cause: HPA can only create pods; the cluster had no headroom and no node autoscaling, and requests were set well above real use. Prevention: cluster autoscaler or Karpenter, PriorityClass for the revenue path so less important pods are preempted, load test capacity before events, alert on Pending pods older than 5 minutes. Success: all 12 pods Running and p99 back under the SLO.

Three advanced questions

A1. You must upgrade a production cluster two minor versions behind. Plan it.

Show answer

Two upgrades, one minor at a time, never skipping. For each: read release notes and the deprecation guide; scan all manifests and Helm charts for removed APIs; check add-on compatibility (CNI, ingress, CSI, metrics, operators) and the version skew policy; upgrade a staging cluster that mirrors production and run smoke and load tests; take etcd/Velero backups; announce a window; upgrade the control plane, then node pools with surge, respecting PDBs and zones, one pool at a time; watch SLO dashboards between steps; keep a rollback plan (nodes can be replaced with the old version; control-plane rollback is limited, which is why staging and backups matter). Afterwards, record time taken and issues, and schedule the next upgrade to stay current.

A2. Design CI so a compromised pull request from a fork cannot steal production credentials.

Show answer

Run untrusted PR code on workflows without secrets (pull_request, read-only token), never use pull_request_target to check out and run fork code, require approval for first-time contributors, use OIDC roles whose trust policy only accepts the main branch and a protected environment, pin actions by SHA, set permissions to least, use ephemeral runners, restrict network egress for runners where possible, and separate build (untrusted) from deploy (trusted, reviewed) workflows connected by an immutable artifact digest.

A3. Memory use of a container looks fine but the pod is repeatedly OOMKilled. What else counts toward the limit?

Show answer

The cgroup counts anonymous memory, page cache attributed to the cgroup, kernel memory, tmpfs (emptyDir medium Memory), thread stacks, and, for JVMs, non-heap areas (metaspace, code cache, direct buffers). Compare the container_memory_working_set_bytes metric (what the kubelet uses for eviction) against the limit, check memory.stat, and size heap as a percentage of the limit with headroom (for example MaxRAMPercentage=70). Short spikes between scrapes can hide the peak, so look at max_over_time or lower scrape intervals.

2. Two classes of the day

Class 1: Jenkins in production (pipelines, agents, shared libraries)

Objective: run Jenkins so that the controller stays healthy, builds run on disposable agents, pipelines are code in Git, and common logic lives in a versioned shared library.

Theory. Jenkins has a controller (UI, scheduling, job config, credentials, plugin runtime) and agents (where steps actually run). Rule one: set controller executors to 0, because anything running on the controller can read its secrets and its disk. Rule two: agents should be ephemeral (a Kubernetes pod or cloud VM per build), so builds do not share dirty workspaces. A Pipeline is a Jenkinsfile stored in the repository; Declarative syntax (pipeline { stages { ... } }) is the default choice for its structure and validation, Scripted (Groovy) is the escape hatch. A Multibranch Pipeline discovers branches and PRs and builds each with the Jenkinsfile on that branch.

Important details that bite: Jenkins runs pipeline Groovy through the CPS interpreter, so heavy logic in Groovy is slow and its state must be serializable (the famous NotSerializableException); push real logic into scripts or sh steps. Use post { always { ... } } for cleanup and notifications, options { timeout(...); disableConcurrentBuilds(); buildDiscarder(...) } to bound resources, and lock or milestone to stop out-of-order deploys. Credentials come from the credentials store through withCredentials (values are masked in logs, but a script can still print them encoded, so restrict who edits Jenkinsfiles on protected branches). Plugins are your largest risk: each is code running in the controller with its own CVEs. Keep a short list, update on a schedule, and read the Jenkins security advisories.

Shared libraries let many repos reuse a pipeline: a Git repo with vars/deployService.groovy (global step) and src/ (classes), loaded with @Library('platform-lib@v1.4.0') _. Pin a tag, not main, so a library change cannot break every pipeline at once, and test the library on a canary job first.

Class 2: CI/CD design in production (GitHub Actions and GitLab CI)

Objective: design a pipeline that builds one artifact, proves it, and promotes the same artifact to production without long-lived cloud keys.

Theory. Good pipeline design has five rules. (1) Build once, promote the digest: tag by git SHA, deploy the image digest (app@sha256:...); environments differ only in configuration. (2) Fast feedback first: lint and unit tests in parallel in the first few minutes; slow integration and security deep-scans later or on merge, with a required gate under about ten minutes. (3) Least privilege: the workflow token gets permissions: contents: read by default and only widens per job. (4) No static cloud keys: use OIDC federation, where the CI job presents a short-lived signed identity token and the cloud (AWS IAM role, Azure federated credential, GCP workload identity) exchanges it for temporary credentials, restricted by repo, branch or environment claims. (5) Supply-chain hygiene: pin third-party actions to a full commit SHA (tags can be moved; the March 2025 compromise of the tj-actions/changed-files action showed this), and never run untrusted PR code with secrets (pull_request_target plus a checkout of the PR head is the classic mistake).

GitHub Actions vocabulary: workflow, job, step, runner (GitHub-hosted or self-hosted), environment (with required reviewers and environment secrets), reusable workflows (workflow_call) and concurrency. GitLab CI equivalents: .gitlab-ci.yml, stages and jobs, runners (shared, group, project), environment: with protected environments, include: and CI/CD components for reuse, rules: for conditional jobs, and id_tokens for OIDC. Self-hosted runners are cheaper at scale but are your security boundary: use ephemeral runners, never attach them to public repos, and isolate per trust level.

PR -> [lint | unit | sast] parallel -> build image (tag=sha, SBOM, scan)
  merge to main -> push to registry -> deploy staging (OIDC role A) -> smoke tests
                -> prod job: environment "production" (required reviewer, OIDC role B)
                -> canary 10% -> verify SLO -> 100%      rollback = redeploy previous digest

name: ci
on: { pull_request: {}, push: { branches: [main] } }
permissions: { contents: read }

Scenario A (today's tools): the Jenkins agents pegged at 100% CPU and builds crawl

Situation. Saturday 14:10 IST. Release builds that took 8 minutes now take 35. The Jenkins queue shows 40 jobs waiting. Alert: "agent pool CPU above 95% for 20 minutes". Nothing was deployed to Jenkins itself; a developer merged a change to the shared library on Friday evening.

$ uptime
 14:12:03 up 21 days, load average: 38.2, 35.9, 30.1      (nproc = 8)
$ top -b -n1 | head -12
  PID USER  %CPU %MEM COMMAND
 8841 jenkins 790  2.1 java -jar agent.jar
 9120 jenkins 395  0.4 node /home/jenkins/ws/web/node_modules/.bin/jest
$ ps -eo pid,etimes,cmd --sort=-%cpu | grep -c jest
 23
$ mpstat -P ALL 1 1     # %usr 91  %sys 7  %iowait 0.3  %steal 0.0

Constraints: you cannot restart the whole pool (a production release is in the queue); you may kill individual builds; the library change is already on main.

Guiding questions: 1) Is this CPU-bound, I/O-bound or steal? Which numbers prove it? 2) Why would 23 jest processes exist on 8 vCPUs, and what could the library change have done? 3) What is the safe immediate fix and the permanent one?

Show solution

Investigation. 1) Classify: load 38 on 8 CPUs, %usr 91, %iowait 0.3, %steal 0.0 means real user-space CPU demand, not disk and not a noisy neighbour. 2) Find who: ps -eo pid,ppid,etimes,pcpu,cmd --sort=-pcpu | head -30 and pstree -p 8841 show 23 jest worker trees. cat /proc/8841/cgroup or the agent pod spec shows no CPU limit. 3) Why many: jest defaults to roughly one worker per core per run; with executors set to 4 per agent, 4 runs x 8 workers each = 32 workers on 8 vCPUs. git log -p -- vars/ on the shared library shows Friday's change replaced jest --runInBand with jest --maxWorkers=100% and raised executors in the agent template from 2 to 4. 4) Check it is not malware or a loop: processes are children of the Jenkins agent, working directories match job names, and no unknown binaries (ls -l /proc/PID/exe).

Root cause. An unreviewed library change multiplied parallelism beyond the agent size; with no CPU limits, context switching and thrashing made each build slower than serial execution, and the queue grew.

Fix. Immediate: stop the lowest-priority queued and running jobs from the Jenkins UI (not kill -9 on the agent), then pin pipelines to the previous library tag with @Library('platform-lib@v1.3.2') via the default version setting in Jenkins, which needs no restart. Permanent: set --maxWorkers to a number derived from the pod CPU request, set CPU requests and limits in the agent pod template (so the scheduler spreads pods), release the library through tags with a canary job, and add an alert on queue time (not only CPU). Prevention: required review from the platform team on vars/, a smoke pipeline that runs on library PRs and records duration, CPU saturation visible per pod on a dashboard (container_cpu_cfs_throttled_periods_total if limits are set).

Scenario B (senior level): a Java service in Kubernetes is OOM-killed every few hours

Situation. The payments-api (Java 21, 6 replicas) restarts about every 3 to 5 hours; error rate spikes to 2% each time. Dashboard memory looks flat at about 70% of the 2 GiB limit, then drops. The team's first proposal is "double the limit to 4 GiB".

$ kubectl get pods -l app=payments-api
payments-api-7c9d...  1/1  Running  7 (38m ago)
$ kubectl describe pod payments-api-7c9d... | grep -A6 'Last State'
    Last State: Terminated   Reason: OOMKilled   Exit Code: 137
$ kubectl top pod payments-api-7c9d...   ->  1890Mi
$ kubectl exec payments-api-7c9d... -- jcmd 1 VM.native_memory summary | grep -E 'Java Heap|Thread|Class|Code|Internal'
 Java Heap (reserved=1536MB, committed=1536MB)   Thread (committed=310MB, 1190 threads)
 Class (committed=95MB)   Code (committed=60MB)
# JVM flags: -Xmx1536m  (set by a developer), container limit 2Gi

Constraints: no code change can ship before Tuesday; cost matters; customers see errors at each kill.

Guiding questions: 1) Why is the container killed when the heap never exceeds -Xmx? 2) What distinguishes a heap leak from an off-heap or thread leak using the data? 3) What do you change now, what long term, and who needs to hear about it?

Show solution

Investigation. 1) OOMKilled with exit 137 means the kernel's cgroup OOM killer fired because the whole container exceeded its memory limit, not because Java threw OutOfMemoryError. The cgroup counts heap plus thread stacks, metaspace, code cache, direct buffers and the page cache charged to it. Here heap committed 1536 MB + threads 310 MB + class 95 MB + code 60 MB is already about 2 GB, so almost no room remains. 2) -Xmx was set to 75% of the limit, and the remaining 25% (512 MB) is smaller than the non-heap needs. 3) 1190 threads is abnormal for this service (the usual figure is about 200): jcmd 1 Thread.print | grep -c 'pool-' and a thread dump show a growing set of threads from an HTTP client created per request and never closed. Each thread reserves a stack (about 1 MB by default) that becomes resident as used. 4) Confirm with a time series: container_memory_working_set_bytes rising with jvm_threads_live_threads, and check the node's kernel log dmesg -T | grep -i 'killed process' to see the cgroup kill and the memory breakdown. 5) Note the dashboard issue: averaging across 6 pods and a 5-minute scrape hid the saw-tooth; look at per-pod max.

Root cause. A thread leak (new executor per outbound call) pushed non-heap memory up until the total exceeded the 2 GiB cgroup limit; the heap setting left too little non-heap headroom. Doubling the limit would only delay the kill.

Fix. Now: use percentage-based sizing (-XX:MaxRAMPercentage=60 instead of a fixed -Xmx) and raise the limit modestly to 2.5 GiB as a bridge; add a preStop sleep and a PodDisruptionBudget so restarts do not drop in-flight requests; set a liveness restart tolerance and reduce the blast radius with a maxUnavailable of 1. Long term: fix the client lifecycle (one shared client, bounded pool), add Native Memory Tracking (-XX:NativeMemoryTracking=summary) in staging, alert on rate(kube_pod_container_status_restarts_total[1h]) and on thread count, and add a load test that runs 6 hours. Tell the product owner the error rate cause and ETA, tell the finance owner there is a small temporary cost.

4. Interview practice (Linux and networking)

Q1. Users say a website on your Linux server is slow, and SSH is also laggy. What would you do?

Show answer

1) Stay calm and get a quick picture: uptime (load vs nproc), top or htop, free -m, df -h and df -i. 2) Classify the bottleneck with vmstat 1 5 and mpstat -P ALL 1: high us/sy is CPU, high wa is disk, high si/so or low free memory is swapping, high st is a noisy host (VM). Check iostat -x 1 for disk await and /proc/pressure/* (PSI) for stalls. 3) Find the culprit: ps aux --sort=-%cpu | head, pidstat 1, ss -s for connection counts. 4) Check dmesg -T | tail and journalctl -p err -b for OOM kills or disk errors. 5) Mitigate with the least risky action (renice, stop a runaway batch job, scale out, fail over), then record the evidence and root cause. What the interviewer is checking: a method (classify, then drill down), the right tools, and caution before killing processes.

Q2. An application cannot reach db.internal:5432 from a server, but a colleague can from another server. How do you troubleshoot?

Show answer

Walk the path layer by layer. 1) DNS: dig db.internal and getent hosts db.internal (the second uses the same resolver path as the app, including /etc/hosts and nsswitch); compare answers with the colleague. 2) Routing: ip route get <db-ip>, then ping (may be blocked, do not rely on it). 3) Port: nc -vz <db-ip> 5432 or curl -v telnet://...: "refused" means the host answered and nothing listens or a reject rule exists; a timeout means packets are dropped (firewall, security group, NACL, route). 4) Capture: tcpdump -ni any host <db-ip> and port 5432: SYN with no SYN-ACK points to a drop upstream; SYN-ACK returned but app fails points to local rules or TLS. 5) Check local rules (iptables -S or nft list ruleset) and, in the cloud, security groups, NACLs and the DB's own allow-list (pg_hba.conf). The difference between the two servers (subnet, SG, source IP) usually explains it. Checking: layered thinking, distinguishing refused from timeout, and using packet capture to prove where it dies.

Q3. df -h shows the root disk 100% full, but du shows only 40% used. What happened?

Show answer

Usual causes: (1) deleted files still held open by a running process (a log was removed but the process keeps writing): find with lsof +L1 or lsof | grep deleted; free the space by restarting the process or truncating through /proc/PID/fd/N (: > /proc/PID/fd/N). (2) Space hidden under a mount point: files written to a directory before a volume was mounted over it; unmount or bind-mount the root to inspect. (3) Inode exhaustion: df -i at 100% while blocks are free. (4) Reserved blocks or snapshots on LVM or btrfs. Fix the cause (log rotation with copytruncate or proper reopen signals, limits on journald, alert at 80%), not only the symptom. Checking: understanding that a file lives until the last descriptor closes, plus knowing the second tools (lsof, df -i).

6. AIOps: automated incident detection

How it helps. Static thresholds miss slow drifts and fire on normal spikes. Anomaly detection learns a baseline (seasonality by hour and weekday) and flags deviations in error rate, latency or log patterns; a good setup combines it with SLO burn-rate alerts so the page means "users are hurt". Tools: Prometheus with recording rules and burn-rate alerts (start here), Grafana adaptive features, Datadog Watchdog, Elastic and OpenSearch anomaly detection. Example prompt: "Here are 24 hours of p95 latency and error rate for the checkout service at 1-minute resolution (CSV), with deploy times. Risks and guardrails: anomaly detectors flag harmless events (a marketing campaign) and learn bad baselines if an incident is in the training window; keep a human-readable rule beside any model signal, measure precision (how many pages were real) per month, never let the model silence an SLO alert, and keep customer data out of external prompts.

Terraform: remote state and locking

What it is: state is Terraform's record of what it manages; a remote backend stores it centrally with a lock. Why it matters: two applies at once, or state on a laptop, corrupt or lose infrastructure records. How it works:

terraform apply -> acquire lock (S3 lockfile / DynamoDB / Blob lease)
                -> read state -> plan -> change cloud -> write state -> release lock

Split state by blast radius (network, data, apps), enable versioning on the bucket, encrypt it (state holds secrets in plain text), and restrict who can read it. terraform force-unlock is for a crashed run only, after you confirm nobody is applying. AI prompt: "Given this plan output, list resources to be destroyed or replaced and why; flag any that hold data." Ref: S3 backend.

AWS: a VPC route table decides public versus private

What it is: a VPC is your private network; subnets sit in one AZ each; route tables say where traffic goes. Why it matters: "public subnet" is only a route to an internet gateway, and misreading that exposes databases. How it works:

public subnet : 0.0.0.0/0 -> igw-...      (+ public IP needed)
private subnet: 0.0.0.0/0 -> nat-... (in a public subnet, one per AZ for HA)
data subnet   : no default route; reach only via SG from the app tier

Use one NAT gateway per AZ in production (cross-AZ NAT costs data fees and is a single point of failure) and gateway endpoints for S3 and DynamoDB to avoid NAT charges. AI prompt: "Here is my VPC route table export; which subnets can reach the internet inbound, and which have no egress?" Ref: VPC route tables.

Azure: VNets, subnets and peering

What it is: a virtual network (VNet) is a regional private address space split into subnets; NSGs filter traffic; peering links VNets. Why it matters: overlapping address ranges cannot be peered, and peering is not transitive, so hub-and-spoke needs planning. How it works:

spoke-A VNet 10.1.0.0/16 <-peering-> hub VNet 10.0.0.0/16 <-peering-> spoke-B 10.2.0.0/16
A cannot reach B unless the hub routes it (firewall/NVA + user-defined routes)

Plan non-overlapping CIDR blocks for every network, cloud and on-premises, before the first deployment; renumbering later is painful. Use private endpoints for PaaS services. AI prompt: "Check these VNet CIDRs for overlap and propose a non-overlapping plan for 5 spokes." Ref: VNet peering.

1. A private-subnet instance in AWS cannot reach the internet. What do you check?

Show answer

The subnet's route table has a default route to a NAT gateway; the NAT gateway sits in a public subnet whose route goes to an internet gateway and has an Elastic IP; the security group allows outbound; the NACL allows outbound and return traffic (ephemeral ports).

Show answer

Both read the same state, change infrastructure and write conflicting states. A remote backend with locking lets only one run proceed; CI should serialise applies per state, with plan reviewed before apply.

Show answer

VNet peering is not transitive. Route through a firewall or network virtual appliance in the hub with user-defined routes (or use a virtual WAN), and allow forwarded traffic on the peerings and in NSGs.

10. AI pro: structured outputs and JSON schema validation

Concepts. Free-text model output is unsafe to parse in automation. Structured outputs make the model return data that follows a JSON Schema: either through a response-format option that constrains generation to the schema, or through tool definitions with strict enabled so tool names and arguments are schema-valid. Both use grammar-constrained decoding, so the output is syntactically valid, but constrained decoding guarantees shape, not truth: a valid JSON can still name the wrong service.

Design pattern. Treat the model as an untrusted parser in front of your system: (1) define a small, closed schema (enums instead of free strings, required fields, bounded lengths, additionalProperties: false); (2) generate with the schema option; (3) validate again in your code with a schema library (for example Pydantic or jsonschema), because supported schema features are limited by the provider and a refusal or truncation can still occur; (4) apply business checks (does this service exist? is this action in the allow-list?); (5) route failures to a retry with the error message once, then to a human.

ALERT_SCHEMA = {"type": "object", "additionalProperties": False,
  "required": ["severity", "suspected_service", "evidence", "confidence"],
  "properties": {
    "severity": {"enum": ["SEV1", "SEV2", "SEV3", "NOISE"]},
    "suspected_service": {"type": "string", "maxLength": 64},
    "evidence": {"type": "array", "items": {"type": "string", "maxLength": 200}, "maxItems": 5},
    "confidence": {"enum": ["low", "medium", "high"]}}}

result = call_model(prompt, schema=ALERT_SCHEMA)       # constrained generation
data = validate(result, ALERT_SCHEMA)                  # re-validate yourself
if data["suspected_service"] not in KNOWN_SERVICES: escalate_to_human(data)

Trade-offs. Strict schemas reduce parsing bugs and retries and make evaluation easy (compare fields), but a very tight schema can force the model to pick a wrong enum when none fits, so always include an "unknown" or "other" value. Large or deeply nested schemas add latency on the first request (the grammar is compiled and cached by the provider) and some keywords (for example numeric ranges or complex regexes) may be unsupported, so check the current limits. Failure modes: valid but wrong content; silent truncation at max tokens producing incomplete JSON when constrained mode is off; schema drift between the prompt, the code and the downstream consumer; free-text fields that carry prompt injection into the next system (for example an "evidence" string pasted into a shell command). Evaluation, security, cost. Keep a golden set of inputs with expected fields and measure per-field accuracy, not only "valid JSON" rate; version the schema like an API; never execute model-supplied strings, map enums to fixed actions instead; schema tokens count as input, so keep descriptions short, and caching the stable prefix (yesterday's topic) reduces their cost. Sources: Anthropic: structured outputs · Anthropic: strict tool use · JSON Schema Confirmed (pages found in search today; field names change, check the docs).

Important interview questions (8) with detailed answers

1. Explain load average of 12 on a 4-core machine. Is it bad?

Show answer

Load average is the average number of tasks runnable or in uninterruptible sleep (usually disk or NFS waits) over 1, 5 and 15 minutes. 12 on 4 cores means 3 tasks per core waiting, so it is queued, but whether it is "bad" depends on cause: check vmstat (r column, wa), PSI (/proc/pressure/cpu) and latency. A 15-minute value lower than the 1-minute value means it is recovering. High load with idle CPU points to I/O wait.

2. What is the difference between kill -15 and kill -9, and why does it matter in containers?

Show answer

SIGTERM (15) can be handled so the app finishes requests and closes connections; SIGKILL (9) cannot be caught and the kernel ends the process immediately. Kubernetes and docker stop send SIGTERM, wait the grace period (30 seconds by default in Kubernetes), then SIGKILL. If the app is not PID 1 (shell-form ENTRYPOINT) it never gets SIGTERM, so shutdown is abrupt; use exec form or an init such as tini.

3. How do you make a deploy script safe to run twice?

Show answer

Check state before acting (is this release already deployed?), use idempotent operations (mkdir -p, declarative tools), take a lock (flock) so two runs cannot overlap, write to a temp location and switch atomically (symlink or rename), run with strict mode and a --dry-run, log with timestamps and exit with meaningful codes, and make rollback a first-class path.

4. A developer force-pushed over main. How do you recover and prevent a repeat?

Show answer

Find the previous tip: from the GitHub UI (events and branch activity), from any clone with git reflog or from CI logs listing the SHA, then restore with git push origin <old-sha>:main (temporarily allowed by an admin). Prevent with branch protection or rulesets: no force pushes, no deletion, required reviews and checks, restrict who can push, and use --force-with-lease on personal branches only.

5. Why must Jenkins controller executors be 0?

Show answer

Builds on the controller run with its file-system access and can read credentials, job configuration and secrets in JENKINS_HOME, and a runaway build can take the controller down for everyone. Agents isolate builds, can be ephemeral and scale independently.

6. How do you give a pipeline access to AWS without storing keys?

Show answer

OIDC federation: register the CI provider as an identity provider in IAM, create a role whose trust policy checks the token's audience and subject (repository and branch or environment), and let the job call AssumeRoleWithWebIdentity for temporary credentials. Grant the role only the permissions the job needs, and use different roles for staging and production.

7. What does pipefail do and why does a pipeline hide failures without it?

Show answer

A pipeline's exit status is that of the last command by default, so failing_cmd | tee log returns 0. With pipefail the status is that of the rightmost command that failed. Use it with -e and -u, and remember -e is ignored in conditions and after &&.

8. Build once, deploy many: why and how?

Show answer

Rebuilding per environment can produce different binaries from different dependencies, so tests prove nothing about what runs in production. Build one image tagged with the commit SHA, store the digest, scan and sign it, and promote that digest through environments with configuration injected separately (env vars, config maps, secrets). Rollback is redeploying the previous digest.

Two troubleshooting exercises

Exercise 1: a nightly backup script is "successful" but the backup is empty. The cron job runs pg_dump db | gzip > /backup/db.sql.gz; echo done. Monitoring shows exit 0 every night; yesterday's restore test failed because the file is 20 bytes. Find the causes and fix.

Show solution

The pipeline has no pipefail, so a pg_dump failure (for example authentication expired after a password rotation) is hidden by gzip returning 0; echo done runs regardless. A 20-byte gzip is an empty archive. Investigate: run the command manually as the cron user (sudo -u postgres env -i bash -c '...', because cron has a minimal environment), read pg_dump stderr (cron mails or discards it), check ~/.pgpass. Fix: write to a temp file with strict mode, check size and a trailer, then move atomically.

#!/usr/bin/env bash
set -Eeuo pipefail
tmp=$(mktemp /backup/.db.XXXXXX); trap 'rm -f "$tmp"' EXIT
exec 9>/var/lock/db-backup.lock; flock -n 9 || { echo "already running" >&2; exit 1; }
pg_dump --no-password db | gzip -9 > "$tmp"
[ "$(stat -c %s "$tmp")" -gt 1048576 ] || { echo "backup suspiciously small" >&2; exit 2; }
gzip -t "$tmp" && mv "$tmp" "/backup/db-$(date +%F).sql.gz"

Prevention: alert when no new backup file appears or the size drops by more than 50%, and run an automated weekly restore test (a backup is not real until restored).

Exercise 2: GitHub Actions deploy job fails with "Not authorized to perform sts:AssumeRoleWithWebIdentity" after the repo was renamed. It worked last week. Find the cause.

Show solution

The IAM role's trust policy condition on the token sub claim still matches the old name, for example repo:org/old-name:ref:refs/heads/main; the new token says repo:org/new-name:.... Check by printing the claims (decode the token in a debug job or read the CloudTrail AssumeRoleWithWebIdentity failure) and compare with the trust policy (aws iam get-role --role-name ci-deploy). Also verify: the job has permissions: id-token: write, the audience is sts.amazonaws.com, and an environment-scoped subject (environment:production) matches. Fix the trust policy to the new repository name (keep it as narrow as before; do not widen to repo:org/* to make it work), and add a note to the repo-rename checklist.

2. Two classes of the day

Class 1: Shell scripting for production (strict mode, traps, idempotency)

Objective: write a Bash script that you can run twice, that fails loudly, cleans up after itself and cannot run two copies at once.

Theory. Bash is glue, not a language for logic; use it for sequencing commands and switch to Python when you need data structures or tests. Production rules, in order of how often they bite. (1) Strict mode: set -Eeuo pipefail. -e exits on a failing command, -u errors on unset variables, pipefail makes a pipeline fail if any stage fails (otherwise migrate | tee log hides a migrate failure), -E lets the ERR trap fire inside functions. (2) Know where -e is silent: it is ignored inside if conditions, on the left of &&/||, and in local x=$(cmd) (the exit status of local wins; declare then assign). Greg's wiki BashFAQ/105 lists the traps; treat set -e as a safety net, not as error handling. (3) Quote everything: "$var"; unquoted variables split on spaces and glob. (4) Guard destructive paths: rm -rf "${BUILD_DIR:?}/"* aborts if the variable is empty, which prevents the classic rm -rf /*. (5) Traps: trap cleanup EXIT runs on success, failure and most signals; use mktemp for temp files. (6) Idempotency: check state before changing it (mkdir -p, grep -q || echo >>, "if release already deployed, exit 0"). (7) Locking: flock stops two cron or CI runs overlapping. (8) Logging: logs and errors to stderr with timestamps, a --dry-run flag, exit codes that mean something. (9) Run ShellCheck in CI; it catches most quoting and logic bugs.

 trigger (CI / cron / human)
        |
   +----v-----------------------------+
   | lock (flock) -> validate inputs  |  fail fast, exit 2
   | dry-run? print plan, exit 0      |
   | do change (idempotent steps)     |  each step checks state first
   | verify (health check)            |  fail -> rollback function
   +----+-----------------------------+
        v  trap EXIT: cleanup temp, release lock, log result

In real companies. Seniors keep scripts in Git, lint them with ShellCheck, run them from CI (not laptops) with least-privilege credentials, and replace anything over about 100 lines or with real branching logic with Python or a proper tool (Ansible, Terraform). The scripts that survive are boring: small, idempotent, with --dry-run.

#!/usr/bin/env bash
set -Eeuo pipefail
IFS=$'\n\t'
readonly APP="${1:?usage: deploy.sh <version> [--dry-run]}"
DRY="${2:-}"
log() { printf '%s %s\n' "$(date -u +%FT%TZ)" "$*" >&2; }
tmp="$(mktemp -d)"
cleanup() { rc=$?; rm -rf "${tmp:?}"; log "exit rc=$rc"; }
trap cleanup EXIT
trap 'log "failed at line $LINENO"' ERR

exec 9>/var/lock/deploy.lock
flock -n 9 || { log "another deploy is running"; exit 2; }

current="$(cat /opt/app/current_version 2>/dev/null || true)"
[[ "$current" == "$APP" ]] && { log "already on $APP, nothing to do"; exit 0; }
if [[ "$DRY" == "--dry-run" ]]; then log "would deploy $APP (now $current)"; exit 0; fi

retry() { local n=0; until "$@"; do ((++n>=3)) && return 1; sleep $((n*2)); done; }
retry curl -fsS -o "$tmp/app.tgz" "https://artifacts.example.com/app-$APP.tgz"
sha256sum -c <(curl -fsS "https://artifacts.example.com/app-$APP.sha256") --status || { log "checksum mismatch"; exit 1; }
# ... unpack, switch symlink, restart, health check, rollback on failure

Class 2: Git and GitHub: branching strategies, PR reviews, protected branches

Objective: design the branch and review rules so that nothing reaches production unreviewed and tested, and recover calmly when something does.

Theory. Git stores snapshots; a branch is a movable pointer. Three strategies you will meet. Trunk-based development: short-lived branches (hours to 2 days) merged to main many times a day, unfinished work hidden behind feature flags; fits continuous delivery and is what DORA research associates with high performance. GitHub flow: branch, PR, review, merge to main, deploy; the common default. GitFlow: long-lived develop, release and hotfix branches; heavy, suits versioned products shipped to customers, painful for web services because long-lived branches mean big, risky merges. Senior view: the real variable is batch size and branch lifetime; small and frequent merges are safer than big and rare ones.

Merge methods. Merge commit (keeps the branch shape), squash (one commit per PR, clean main, easy to revert one unit), rebase-and-merge (linear, each commit kept). Squash is the usual choice for services because git revert of one commit undoes the whole PR. Reverting a merge commit needs git revert -m 1 <merge-sha> (choose the mainline parent).

Protection. On GitHub use branch protection or the newer rulesets (can be applied org-wide): require a PR, require N approvals, dismiss stale approvals on new commits, require status checks (build, test, scan) and branches up to date, require CODEOWNERS review for sensitive paths (/terraform/, /.github/workflows/), block force-push and deletion, require signed commits or linear history if you need it, use a merge queue on busy repos so main is always green, and apply the rule to admins too. Review culture: small PRs (under about 400 changed lines), a description that says why, reviewer checks behaviour, tests, security and rollback, not formatting (linters do that).

 feature/x --PR--> [ required: review + CI checks + CODEOWNERS ] --> main
     ^                         | fail                                  |
     +---- push fixes ---------+                                       v
 hotfix: branch from main tag, same rules, revert-first culture   deploy (tag)
 Recovery tools: git revert | git reflog | git bisect | git cherry-pick

git switch -c feature/payment-retry
git commit -s -m "Retry payment on 503 (max 3)"      # -s sign-off, add -S to GPG/SSH-sign
git push -u origin HEAD && gh pr create --fill
git revert -m 1 <merge-sha>        # undo a merge commit safely
git reflog                          # find a commit after a bad reset
git bisect start; git bisect bad; git bisect good v1.4.0   # find the breaking commit
git rebase --onto main old-base feature     # move a branch off a stale base
git log --oneline --graph --decorate -20
gh api repos/OWNER/REPO/branches/main/protection | head      # inspect the rules (needs admin)

In real companies. Rules live as code (Terraform GitHub provider or org rulesets) so settings do not drift, and an "emergency bypass" exists but is logged and reviewed afterwards. psql -h orders-db -c "select * from schema_migrations order by version desc limit 3"

Mitigate first. Because the migration never applied, 4.12 and the schema agree, so rollout undo is safe. Had the migration applied a destructive change (dropped or renamed column), rollback of code alone would break, which is why schema changes follow expand and contract: add the new column (compatible with old code), deploy code that uses it, and only in a later release remove the old one. After the undo, 5xx fell to baseline at 16:21.

Fix. Add set -Eeuo pipefail; run the migration as a separate pipeline stage that must pass before the deploy stage; add a post-deploy smoke test and automatic rollout undo if the error rate rises (progressive delivery or a verify step); migrations tested against a copy of production schema in CI.

Decision rule (agreed before the incident). Ride it out when only one AZ is affected (drain it and scale in the others), or when the failover risk (data loss from replica promotion, untested path) exceeds the outage cost. Promoting the replica ends replication; the old region's later writes can be lost (RPO) and failback is a new migration.

Dependencies that break failover. The control plane is often impaired when the data plane is not: if IAM, STS or the provider API fails, scripts that need new credentials or launch capacity will fail, and capacity in the DR region is not guaranteed unless reserved or already running (warm standby). Keep break-glass credentials and the runbook outside the primary region.

Execution. Communicate every 30 minutes on the status page and internal channel with: what we know, what we do, next update time.

Prevention. Quarterly game-day failover with timing; multi-AZ by default and region failover only for tier-1 services; static stability (do not need to launch capacity to survive); DR runbook and credentials outside the primary region; pre-agreed decision criteria and an owner who may press the button.

4. Interview practice (intermediate DevOps)

Q1. Your CI pipeline takes 40 minutes and developers have started to merge without waiting. What would you do?

Show answer

1) Measure first: get per-stage timings from the CI tool and find the longest path; do not guess. 2) Quick wins: cache dependencies and Docker layers, use a pinned slim base image, run unit tests, lint and scans in parallel, shard slow test suites across runners, cancel superseded runs on the same branch (concurrency). 3) Run only what a change needs (path filters, affected-module tests), move slow end-to-end and security deep-scans to a post-merge or nightly job while keeping a fast required gate (target under 10 minutes). 4) Check runner capacity: queue time is often the real delay; use autoscaling ephemeral runners. 5) Track the median and p90 pipeline time as a metric and share it. 6) Do not remove the checks that protect main just to be fast. What the interviewer is checking: data-driven approach, knowledge of caching and parallelism, and a balance between speed and safety.

Q2. You find an AWS access key committed to a public GitHub repo 20 minutes ago. What do you do?

Show answer

1) Treat it as compromised immediately; do not first clean Git history. 2) Revoke or deactivate the key now, then check CloudTrail for what it did since the commit (new users, EC2 launches, S3 reads, region changes). 3) If activity looks suspicious, escalate to security, rotate related secrets, and follow the incident process. 4) Then remove the secret from the repo and history (git filter-repo or BFG), knowing that forks and caches may still hold it, so rotation is the real fix. 5) Prevention: secret scanning and push protection on GitHub, pre-commit hooks (gitleaks), short-lived credentials via OIDC and IAM roles instead of static keys, and a blameless write-up. Checking: revoke before cleanup, awareness that history rewriting does not un-leak, and preventive design.

Q3. A release needs a database column renamed with zero downtime. How do you do it?

Show answer

Use expand and contract in several releases. 1) Expand: add the new column (nullable or with default), keeping the old one. 2) Deploy code that writes to both and reads the old; backfill existing rows in batches to avoid locking. 3) Deploy code that reads the new column; verify. 4) Stop writing the old column. 5) Contract: drop the old column in a later release once no running version uses it. Each step is backward compatible so a rollback of code at any point still works; migrations are tested against a production-sized copy and run as a separate gated stage. Checking: understanding that code and schema deploy separately, rollback safety, and online-migration discipline.

CI/CD: a pipeline is a promotion path for one artifact

What it is: stages that move a single built artifact toward production. Why it matters: if you rebuild per environment you deploy something you never tested. How it works:

commit -> build once -> unit tests -> scan -> artifact (tag = git sha)
                                         |-> deploy dev -> staging (smoke) -> prod (approval, canary)

Promote the same immutable image digest through environments; only configuration changes. Gate production on approvals and a rollback step. AI prompt: "Review this workflow YAML: does it build once and promote the same artifact? List pinned and unpinned actions."

Docker: layers and the build cache

What it is: an image is a stack of read-only layers, one per Dockerfile instruction. Why it matters: order decides build speed and image size. How it works:

FROM python:3.12-slim      # layer 1 (base)
COPY requirements.txt .    # layer 2: changes rarely
RUN pip install -r requirements.txt   # cached while layer 2 unchanged
COPY . .                   # layer 4: changes every commit

Put rarely changing steps first, so a code change reuses the dependency layer. A changed layer invalidates every layer after it. Use .dockerignore to keep .git and secrets out of the build context. AI prompt: "Reorder this Dockerfile for best cache use and explain each move."

Kubernetes: how a Deployment rolls out

What it is: a Deployment manages ReplicaSets to move pods from the old version to the new. Why it matters: bad probes or limits turn a rolling update into an outage. How it works:

Deployment -> new ReplicaSet (v2) scales up
           -> old ReplicaSet (v1) scales down
   maxSurge / maxUnavailable bound the pace; readiness probe gates traffic

A new pod receives traffic only when its readiness probe passes; kubectl rollout status waits, and kubectl rollout undo returns to the previous ReplicaSet. Set maxUnavailable: 0 for zero-capacity-loss updates. AI prompt: "Explain why this rollout is stuck from the output of kubectl describe deploy and the pod events; give read-only checks."

10. AI pro: prompt caching, batching and cost control

Concepts. LLM cost is mostly tokens in and out. Three levers: (1) prompt caching: the provider stores the processed prefix of your prompt (system rules, tool definitions, a large runbook or document) so later requests that begin with the identical prefix are billed at a reduced rate for those tokens and respond faster; (2) batch processing: submit many non-urgent requests asynchronously for a lower price (for example overnight log classification); (3) right-sizing: use a smaller model for easy steps, cap output length, trim inputs.

Design pattern. Order the prompt from most stable to most volatile, because caching matches an exact prefix: any change early in the prompt invalidates everything after it.

[ tools + system rules ]  stable   \  cache breakpoint here
[ runbook / reference docs ] stable /  (identical across requests)
[ incident-specific logs ]   changes every request  (not cached)
[ user question ]            changes
route: easy classification -> small model (batch, nightly)
       live incident help  -> larger model (synchronous, cached prefix)

Code sketch (Anthropic Python SDK; check the docs for current field names and minimum cacheable lengths):

import anthropic
client = anthropic.Anthropic()          # key from environment, never in code
resp = client.messages.create(
    model="claude-sonnet-5-5", max_tokens=600,
    system=[{"type": "text", "text": RUNBOOK_TEXT,
             "cache_control": {"type": "ephemeral"}}],   # cache the stable prefix
    messages=[{"role": "user", "content": f"Logs:\n{redacted_logs}\nWhat failed?"}],
)
u = resp.usage
print(u.input_tokens, u.cache_creation_input_tokens, u.cache_read_input_tokens)

Trade-offs. Caching has a time-to-live (minutes, refreshed on use; longer options exist), so it pays off only with repeated, close-in-time requests; a cache write can cost a little more than a normal input, so a prompt used once gains nothing. Batches trade latency (results within hours) for price, so they suit offline work, not on-call help. Smaller models are cheaper but less reliable on reasoning; measure on your golden set before switching.

Failure modes. Putting a timestamp or request ID at the top of the prompt, which silently breaks cache hits (watch the cache-read counter, expect near zero if broken); caching content that includes secrets or customer data; unbounded output; retry storms that multiply cost; batch jobs with no result validation.

Evaluation, security, cost. Log per request: input, cache-read, cache-write and output tokens, latency and cost, and alert on cost per request drifting up. Keep a golden set so a cheaper model or a changed prompt cannot lower quality unnoticed. Cached prompts are still sent to the provider: apply the same redaction and data-handling rules. Set per-team budgets and rate limits at your gateway (a later AI pro topic). Check current prices and cache rules on the provider pages before you plan a budget. 2. Two classes of the day

Class 1: Linux processes, systemd, journald and CPU/memory/disk triage

Objective: in 5 minutes on an unknown, unhealthy host, say which resource is the bottleneck (CPU, memory, disk, or I/O) and which process causes it.

Theory. A process is a kernel task with a PID, memory map, file descriptors and a parent. States you must read in ps/top: R running, S sleeping, D uninterruptible sleep (waiting on I/O, cannot be killed, counts in load average), Z zombie (finished, parent has not called wait; harmless unless thousands). Load average counts runnable plus D-state tasks, so a load of 40 with idle CPU means an I/O or NFS problem, not CPU. Memory: "free" is misleading; read MemAvailable in /proc/meminfo. Page cache is reclaimable. When memory runs out the kernel OOM killer picks a victim by oom_score; in containers the cgroup limit triggers it earlier than the host would. Disk: a full filesystem has two forms, blocks (df -h) and inodes (df -i), and a third trap: a deleted file still held open by a process keeps its space (lsof +L1). systemd supervises services as units in cgroups: Restart=, LimitNOFILE=, MemoryMax= are your production levers. journald stores structured logs; filter by unit and time.

 request-> | app (PID) --threads--> CPU            |
           |   |  fds --> sockets / files          |
           |   +--> heap --> RAM --> swap/OOM      |
           |   +--> writes --> page cache --> disk |

Class 2: Linux networking: ss, tcpdump, DNS, iptables/nftables

Objective: locate a network failure at the right layer (DNS, route, firewall, listener, application) with one command per layer.

Theory. Walk the stack bottom-up. L2/L3: ip addr, ip route (which interface and gateway will this destination use: ip route get 10.0.0.5). Name resolution: applications call the resolver per /etc/nsswitch.conf; on modern distros systemd-resolved stands in front, so dig (talks DNS directly) can succeed while the app fails; test with getent hosts name which follows the same path as the app. TCP: a connection is a 4-tuple; states you must know are LISTEN, ESTABLISHED, TIME_WAIT (normal, from the side that closes), CLOSE_WAIT (the remote closed and your app did not: an application bug, a leaked connection) and SYN-SENT (no answer to your SYN: firewall drop or wrong route). "Connection refused" means a host answered with RST (nothing listening); "timed out" means silence (drop, route, security group). Firewall: netfilter hooks (PREROUTING, INPUT, FORWARD, OUTPUT, POSTROUTING); iptables and nftables are front-ends; Kubernetes kube-proxy and Docker both write rules here. Conntrack tables can fill under heavy traffic and drop new connections (nf_conntrack: table full in dmesg).

 client --DNS--> resolver     (dig / getent)
   |--route--> gateway        (ip route get)
   |--SYN----> firewall/SG    (timeout = dropped here?)
   |--------> host:port       (ss -ltnp: is anyone LISTENing?)
   +--------> app             (curl -v: TLS, HTTP status)
 tcpdump on both ends shows where the packet stops.

ss -ltnp                               # listeners and owning process
ss -tan state close-wait | wc -l       # leaked connections
ss -s                                  # summary by state
ip route get 10.20.0.15
getent hosts api.internal; dig +short api.internal @10.0.0.2
curl -sv --max-time 5 https://api.internal/health -o /dev/null
nc -zv 10.20.0.15 5432                 # port reachable?
tcpdump -ni eth0 'host 10.20.0.15 and port 5432' -c 20
mtr -rwc 20 10.20.0.15                 # per-hop loss
iptables -S | head -30; nft list ruleset | head -40
conntrack -S; sysctl net.netfilter.nf_conntrack_max

In real companies. Security groups and NACLs replace host firewalls in the cloud, but the failure shapes are the same. Seniors ask first: refused or timeout? That one word halves the search. Capture packets on the server and the client: if the SYN arrives and no SYN-ACK leaves, the problem is the host; if it never arrives, the network.

Scenario A (today's tools): the production server is down

Symptoms. 02:10 IST: the pager says "orders-api health check failing" on one of two VMs behind a load balancer. The LB removed it; the other VM now runs at 85% CPU. SSH to the failed VM hangs for 20 seconds, then works.

$ top -b -n1 | head -5
%Cpu(s):  3.1 us,  2.0 sy,  0.0 ni,  0.0 id, 94.2 wa

Constraints. Peak traffic at 09:00; you may not reboot the only healthy node; logs are needed for audit for 90 days.

Questions: (1) What does 94% iowait with load 38 tell you, and what do you check next? (2) Why might freeing space by deleting a log not free any space? (3) What permanent changes stop a repeat?

Show solution

Investigation. High iowait plus a full disk means processes are blocked on writes, so load is I/O, not CPU. Find the big consumers and open-deleted files:

du -xh /var/log --max-depth=2 | sort -h | tail
lsof +L1 | grep /var/log           # deleted but still open
df -i /var/log                      # inodes too
journalctl --disk-usage

Result: /var/log/orders/app.log is 41 GB; DEBUG logging was switched on in the 18:00 release, and logrotate had been failing silently because its config referenced a missing group. A previous engineer had also deleted an older log with rm while the app held it open, so that space was never released.

Fix. Compress and move the large log to the archive bucket (audit need), truncate rather than delete the live file (: > app.log or restart the service to release handles), then systemctl restart orders-api; confirm health check green, LB re-adds the node, CPU on the other node falls. Set log level back to INFO.

Prevention. Fix the logrotate config and test with logrotate -d; /var/log on its own volume (done, but without alert); alert at 80% and on predicted full in 4 hours (predict_linear); log level as config checked in review; ship logs off-host so local retention can be 7 days; DEBUG in production needs an expiry.

Scenario B (senior level): Kubernetes node goes NotReady during business hours

Symptoms. 14:20: alert "KubeNodeNotReady" for node ip-10-0-3-17 in a 12-node cluster. Pods on it show Terminating/Unknown. Two minutes later a second node flaps.

$ kubectl get nodes
ip-10-0-3-17   NotReady   <none>  v1.33.x
ip-10-0-3-21   Ready      <none>  v1.33.x

31

Constraints. A StatefulSet database replica is on that node; PodDisruptionBudgets exist; cluster autoscaler is on; no one may delete the node before data is safe.

Questions: (1) What does "kubelet stopped posting status" distinguish between? (2) What happens to the pods and to the StatefulSet pod automatically, and why can that be dangerous? (3) How do you find out why two nodes failed in two minutes?

Show solution

Investigation. NotReady with Unknown conditions means the control plane lost heartbeats (node Lease not renewed): kubelet dead, node frozen, or network cut. Separate them:

kubectl get lease -n kube-node-lease ip-10-0-3-17 -o yaml | grep renewTime
aws ec2 describe-instance-status --instance-ids i-0abc... (or cloud console)
# via SSM/serial console, not SSH if network is suspect:
systemctl status kubelet containerd; journalctl -u kubelet --since "20 min ago" | tail -50
dmesg -T | grep -i -E 'oom|hung task|blocked for more'
kubectl get events -A --sort-by=.lastTimestamp | tail -30

Found: a batch job without memory limits (BestEffort pods) consumed node memory, the kernel starved kubelet and containerd, heartbeats stopped. Both nodes ran the same batch job version.

What Kubernetes does. After the node taint node.kubernetes.io/unreachable and the default 300 s toleration, pods are evicted and controllers recreate Deployment pods elsewhere. A StatefulSet pod is not force-recreated while the node state is unknown, to avoid two writers on one volume; it stays Terminating until the node is confirmed gone. Do not run --force --grace-period=0 on it unless you have proven the old node is dead (stop or terminate the instance first), otherwise you risk split-brain.

Fix. Cordon healthy nodes' batch workload source, stop the batch job, reboot/replace the stuck instance, confirm volume detaches, let the StatefulSet reschedule, verify replication caught up. Restore capacity via autoscaler.

Prevention. LimitRange/ResourceQuota requiring requests and limits per namespace; admission policy rejecting BestEffort in prod; kubeReserved/systemReserved and eviction thresholds on kubelets; separate node pool for batch with taints; PDBs and topology spread; alert on node memory saturation, not only on NotReady.

4. Interview practice (basic DevOps: CI/CD, IaC, Git)

Q1. A developer says "it works on my machine but fails in the pipeline". What would you do?

Show answer

1) Read the failing job log from the first error, not the last line. 2) Compare environments: tool versions, OS, env vars, dependency lock files, container image (is the pipeline using a pinned image?). 3) Reproduce locally by running the same image the runner uses (docker run with the job's command). 4) Check for state differences: cache poisoning, files only on the laptop, secrets or network access the runner lacks. 5) Fix by pinning versions and moving the build into a container so both environments are identical; add the repro steps to the README. 6) If flaky, rerun to see whether it is deterministic before changing code. What the interviewer is checking: method over guessing, knowledge of environment parity and reproducibility.

Q2. Someone ran terraform apply from a laptop and the team's state is now out of sync with reality. What do you do?

Show answer

1) Stop further applies; tell the team. 2) Check that the backend is remote with locking; run terraform plan from the pipeline to see the drift. 3) If real resources were changed by that apply, state in the remote backend is the truth if the laptop used it; if it used a local state, import resources (terraform import or import blocks) and reconcile. 4) Review the diff, decide whether code or reality is right, then align them. 5) Prevention: remote state with locking, apply only from CI, least-privilege credentials so laptops cannot apply, PR review of plans. Checking: understanding of state, locking and why applies belong in CI.

Q3. A bad commit reached main and was deployed. How do you handle it with Git and the pipeline?

Show answer

1) Restore service first: roll back the deployment to the last good artifact (redeploy the previous tag), do not debug in production. 2) In Git use git revert <sha> (a new commit that undoes it, safe on a shared branch) rather than reset --force, which rewrites shared history. 3) Open a PR for the revert, let CI run, deploy. 4) Then root-cause: why did tests and review not catch it? Add a test. 5) Consider branch protection, required checks and a canary stage. Checking: priority of mitigation over diagnosis, safe Git practice, learning loop.

8. Career: the roadmap from DevOps Engineer to Architect

Teacher's lesson. Titles are less important than scope of ownership. A DevOps engineer with 2 to 3 years is trusted with tasks: "add this pipeline stage", "fix this alert". A senior is trusted with outcomes: "deployments for this product are safe and fast". An SRE or platform engineer owns a system and its targets: an SLO, a platform used by other teams. An architect or lead owns direction: standards, cost and risk across teams, and explains trade-offs to people who do not read YAML.

What actually changes at each step: (1) Depth: you no longer stop at "the pod restarted"; you find why, and why nothing warned you. (2) Breadth: you can reason about network, identity, cost and failure modes of a design before it is built. (3) Leverage: you write things that make ten people faster: a module, a template, a runbook, a guardrail. (4) Communication: you give short, honest status updates, state risk and ask for decisions. (5) Judgement: you say no, or "not yet", with reasons.

War story: early in my career I was the fastest person at fixing outages, and I thought that made me senior. My manager showed me the incident list: the same three causes repeated for a year, and I had fixed each one by hand. The senior move would have been to remove the cause once. That is the shift: from fixing to preventing, from being the hero to making heroes unnecessary.

The next 8 weeks give you the technical breadth of a senior (Linux to Kubernetes to cloud to observability to SRE) and the final week the leadership pieces. Each week gives you one artifact you can show in an interview or review: a runbook, a pipeline, a module, a dashboard. Artifacts beat certificates.

Say it like this (to a manager or CTO): "I'm spending the next two months closing my gaps in production troubleshooting, infrastructure as code and reliability, so I can own deployments and incident response for our service end to end; I'll show the result as a runbook, a Terraform module and an SLO dashboard."

10. AI pro: transformer and attention intuition, context windows

Concepts. A transformer processes text as tokens (sub-word pieces). Each token becomes a vector; self-attention lets every token compute weights over earlier tokens (query-key match) and mix their value vectors, so the meaning of "it" depends on the nouns before it. Decoder-only models (the family used for chat and code) generate one token at a time, each conditioned on everything in the context window. The window is the maximum tokens of input plus output the model can see; it is a hard limit, and attention cost grows roughly with the square of length unless optimised.

Design pattern. Treat the context as a scarce, billed, noisy buffer. Put stable instructions first, retrieved facts next, the question last; trim irrelevant logs; summarise long histories.

tokens in  ->  [system rules][retrieved docs][history][user ask]
                         |        context budget (N tokens)
model: attention over all -> next token -> append -> repeat
cost  ~ input tokens + output tokens ; latency ~ output tokens

Trade-offs. Bigger windows allow more evidence but cost more and can dilute attention: models can miss details buried in the middle of very long inputs ("lost in the middle", Liu et al.). Retrieval (RAG) sends only relevant chunks; long context sends everything. Output is sampled, so the same prompt can give different answers; lower temperature for operations tasks.

Failure modes. Truncation when input plus output exceeds the window (silent cut or an error); hallucination when evidence is missing; instruction dilution in long contexts; prompt injection hidden in logs or tickets you paste in; non-determinism breaking tests.

Code sketch (budget guard before calling any model):

def fit(chunks, limit_tokens, count):   # count = your tokenizer
    out, used = [], 0
    for c in sorted(chunks, key=lambda c: -c.score):
        t = count(c.text)
        if used + t > limit_tokens: break
        out.append(c.text); used += t
    return "\n---\n".join(out)

Evaluation, security, cost. Measure tokens per request, p95 latency, and answer quality on a fixed golden set whenever you change prompt or chunking. Treat any text from logs, tickets or the web as untrusted: never let it trigger actions. Cost is roughly proportional to tokens, so deduplicate logs, cap output length, and cache stable prefixes (tomorrow's AI pro topics cover caching). Sources: Vaswani et al., Attention Is All You Need · Liu et al., Lost in the Middle Confirmed

AWS: accounts, regions, AZs, Organizations

What it is: An AWS account is the basic container for your resources and bills. A Region is a geographic area (for example Mumbai, ap-south-1). An Availability Zone (AZ) is one or more separate data centers inside a Region. AWS Organizations groups many accounts under one management account.

Why it matters: Accounts are the strongest isolation boundary (security and cost). Spreading across AZs keeps your app running if one data center fails.

How it works:

Organization (management account)
 ├─ OU: prod  ── account: app-prod
 └─ OU: dev   ── account: app-dev
Region ap-south-1
 ├─ AZ a   ├─ AZ b   └─ AZ c   (separate failure domains)

How to use AI with it: Prompt: "Suggest an AWS Organizations layout with OUs for prod, dev and security for a 10-person team, and explain why each account exists." Safety tip: never paste access keys or account IDs of production into a chat; ask for a design, then apply it yourself.

Docs: What is AWS Organizations · Regions and Availability Zones

Azure: tenants, subscriptions, resource groups

What it is: A tenant is your organization's identity space (Microsoft Entra ID). A subscription is a billing and access boundary inside it. A resource group is a folder for related resources (VMs, databases) that share a life cycle. Management groups sit above subscriptions.

Why it matters: You apply policy, access (RBAC) and budgets at these levels, so a good layout saves you from messy permissions later.

How it works:

Tenant (Entra ID)
 └─ Management group
     └─ Subscription
         └─ Resource group
             └─ Resource (VM, storage, ...)

How to use AI with it: Prompt: "Compare an Azure subscription-per-environment layout with a single subscription and resource groups. List pros and cons for a small team." Safety tip: AI may mix up AWS and Azure terms (an AWS account is closest to an Azure subscription); check against the docs.

Docs: Organize Azure resources

Docker: containers vs VMs

What it is: A container packages an app and its libraries and runs as an isolated process on the host's kernel. A virtual machine runs a full guest operating system on a hypervisor.

Why it matters: Containers start in seconds, use less memory and run the same on a laptop and a server. The trade-off is weaker isolation than a VM because the kernel is shared.

How it works:

VM:         App | Guest OS | Hypervisor | Hardware
Container:  App + libs | Container runtime | Host OS kernel | Hardware

How to use AI with it: Prompt: "Explain in five lines why a container is not a VM, then give me a quiz of three questions." Safety tip: do not run commands from an AI answer with --privileged or by mounting the Docker socket unless you understand why.

Docs: Docker overview

Kubernetes: cluster architecture

What it is: A cluster has a control plane (API server, etcd, scheduler, controller manager) that decides what should run, and worker nodes (kubelet, container runtime, kube-proxy) that run your Pods.

Why it matters: Every kubectl command, deployment and failure ends up in these parts. Knowing them makes troubleshooting faster.

How it works:

kubectl ──> API server ──> etcd (state)
              │  scheduler picks a node
              ▼
        Node: kubelet ──> container runtime ──> Pods

How to use AI with it: Prompt: "Walk through what happens, step by step, when I run kubectl apply -f deploy.yaml." Safety tip: give AI tools read-only cluster access first; never share kubeconfig files or Secrets.

Docs: Cluster architecture

Terraform: declarative IaC, init, plan, apply

What it is: Infrastructure as Code: you write what you want (a network, a VM) in files, and Terraform works out the steps to get there. This is declarative, unlike a script of commands.

Why it matters: Changes are reviewed, repeatable and stored in Git. plan shows the effect before anything changes.

How it works:

terraform init   -> download providers
terraform plan   -> show what will change
terraform apply  -> make the change, record it in state

How to use AI with it: Prompt: "Explain this terraform plan output in plain English and flag anything that destroys or replaces a resource." Safety tip: remove secrets and account IDs from plans before pasting; never let an AI run apply or destroy without your review.

Docs: What is Terraform

CI/CD: CI vs delivery vs deployment

What it is: Continuous Integration merges and tests code often. Continuous Delivery keeps every passing build ready to release with a manual approval. Continuous Deployment releases automatically when tests pass.

Why it matters: Small, frequent, tested changes are safer than big releases, and problems show up early.

How it works:

commit -> build -> test -> (approve?) -> deploy
 CI = commit..test | Delivery = + ready to deploy | Deployment = + auto deploy

How to use AI with it: Prompt: "Here is my pipeline YAML (secrets removed). Which stages could run in parallel, and what is missing: tests, scans, approval?" Safety tip: review AI-edited pipeline files like any code, as they can leak secrets or widen permissions.

Docs: GitLab CI/CD (example tool; concepts apply to Jenkins and GitHub Actions)

AI: what an LLM is, tokens, context

What it is: A large language model predicts the next piece of text (a token, roughly a word fragment) from the text before it. The context window is how many tokens it can consider at once, including your prompt and its answer.

Why it matters: Cost and limits are counted in tokens, and anything outside the context window is not seen. It can sound sure and still be wrong.

How it works:

your prompt -> tokens -> model -> next token -> next token ...
[ system + your text + earlier chat + answer ] must fit in the context window

How to use AI with it: Prompt: "Explain what a Kubernetes Pod is in 5 lines, then list 2 things you are unsure about." Safety tip: check every command and fact against official docs before using it in production.

Docs: Claude documentation

Deep dive of the day: Kubernetes cluster architecture

The idea. Kubernetes keeps your declared wish ("run 3 copies of this app") true. You write the wish as objects; Kubernetes keeps comparing the desired state with the actual state and fixes any difference. This loop is called reconciliation, and nearly everything in the cluster works this way.

The architecture. A cluster has a control plane (the brain) and worker nodes (the muscle).

        kubectl / CI / Argo CD
                 |  (HTTPS, authenticated)
                 v
 +-------------- CONTROL PLANE ---------------+
 |  kube-apiserver  <-->  etcd (state DB)      |
 |      ^    ^                                 |
 |      |    +-- kube-scheduler (picks a node) |
 |      +------- controller-manager (loops)   |
 +---------------------------------------------+
        | watch / report
 +------v-------+  +-------------+  +-------------+
 | Node 1       |  | Node 2      |  | Node 3      |
 | kubelet      |  | kubelet     |  | kubelet     |
 | kube-proxy   |  | kube-proxy  |  | kube-proxy  |
 | runtime      |  | runtime     |  | runtime     |
 | [Pod] [Pod]  |  | [Pod]       |  | [Pod] [Pod] |
 +--------------+  +-------------+  +-------------+

The API server is the only front door; the other parts talk to it, not to each other. etcd stores all cluster state, so back it up. The scheduler only decides which node a new Pod runs on (using resource requests, taints, affinity). Controllers (Deployment, ReplicaSet, Node and more) run the reconcile loops. On each node the kubelet starts containers through a container runtime (such as containerd) and reports health; kube-proxy (or an eBPF network plugin) makes Services reachable.

Real-world example. You run kubectl apply -f deploy.yaml with replicas: 3. The API server validates the Deployment and stores it in etcd. The Deployment controller creates a ReplicaSet, which creates 3 Pod objects with no node. The scheduler assigns each Pod to a node. Each node's kubelet sees "a Pod is assigned to me" and starts it. If a node dies, the node controller marks its Pods lost, the ReplicaSet creates new Pods, and the scheduler places them on healthy nodes. In managed services such as EKS or AKS the provider runs the control plane; you manage the worker nodes.

Common mistakes. (1) One control-plane node in production (use 3 for etcd quorum, or a managed service). (2) No etcd backups on self-managed clusters. (3) Pods with no resource requests, so one noisy Pod can starve others. (4) Giving everyone cluster-admin. (5) Thinking the scheduler restarts containers; that is the kubelet's job. (6) Running retired components: ingress-nginx was retired in March 2026 and a recent CVE got no fix (see today's log), so plan a maintained ingress or Gateway API controller.

Mini exercise (15 min). Install kind or minikube. Run kubectl get nodes, then kubectl get pods -n kube-system and find the API server, etcd, scheduler and controller-manager Pods. Create a Deployment (kubectl create deployment web --image=nginx --replicas=3), then kubectl get pods -o wide to see which node each Pod got. Delete one Pod and watch a new one appear. Run kubectl describe pod <name> and read the Events: "Scheduled" (scheduler), then "Pulled" and "Started" (kubelet). Docs: Cluster architecture.

AI Pro (professional level): transformer attention and context windows

Concepts. A transformer turns text into tokens, maps each token to a vector, and passes them through layers. In each layer, self-attention lets every token compute a weighted mix of other tokens' information. Each token produces a query (Q), key (K) and value (V); the attention weights are softmax(QKT/√d) and the output is those weights times V. Multi-head attention runs several of these in parallel so the model can track different relations (syntax, references, code scope). Chat models are decoder-only with a causal mask, so a token sees only earlier tokens. Primary source: Attention Is All You Need.

Why context windows matter for design. Cost and latency grow with the number of tokens: naive attention work grows roughly with the square of sequence length (implementations use optimisations), and the KV cache (stored K and V of earlier tokens) takes GPU memory in proportion to length. Providers bill input and output tokens, usually at different rates. A large window does not mean equal attention everywhere: models can miss details buried in long inputs, so test this rather than assume it.

request = [ system | tools | docs / retrieved chunks | history | user question ]
            ^ stable prefix (cacheable)             ^ changes every call
budget:  input_tokens + max_output_tokens <= context_window
policy:  trim history -> summarise old turns -> retrieve only top-k chunks

Design pattern. Put stable content (instructions, tool schemas, reference docs) first and volatile content last, so a reusable prefix can be cached by the provider (the next AI Pro topic). Keep a token budget per request and reserve space for the answer. Prefer retrieving a few relevant chunks over pasting whole repositories.

Trade-offs. Long context: simpler pipeline, but higher cost and latency and a risk of distraction. Retrieval: cheaper and more focused, but it can miss facts if chunking or search is poor. Summarising history: saves tokens, but loses detail and can lock in earlier errors.

Failure modes. Silent truncation when you exceed the limit; stale or conflicting facts in a long context; the model following instructions hidden in retrieved text (prompt injection); cost spikes when an agent loop keeps appending tool output to the history.

Sketch (token budget guard, Python):

MAX_CTX, RESERVE = 200_000, 4_000   # example numbers; use your model's real limits
def build(messages, count_tokens):
    budget = MAX_CTX - RESERVE
    kept, used = [], 0
    for m in reversed(messages):          # keep newest turns first
        t = count_tokens(m)
        if used + t > budget:
            break
        kept.append(m); used += t
    return list(reversed(kept))           # system prompt is added separately

Evaluation, security, cost. Evaluate with a golden set that places the key fact at the start, middle and end of the context and checks the answer. Log input and output tokens per request and alert on p95 growth. Treat anything retrieved or returned by a tool as untrusted data; it must never change tool permissions. Measure cost before choosing a bigger window.

Day 2: Cloud Networking (AWS VPC vs Azure VNet)

Today's goal: understand how cloud networks isolate and connect your workloads, and how AWS and Azure name the same ideas.

1. Theory: what, why, how

  • What: a virtual private network you define in software. AWS calls it a VPC, Azure a Virtual Network (VNet). You choose an IP range (CIDR, e.g. 10.0.0.0/16) and split it into subnets.
  • Why: isolation (servers are not on the open internet by default), control over who talks to whom, and a place to connect to on-premises networks.
  • How: subnets + route tables decide where traffic goes; firewalls (security groups / NSGs) decide what is allowed; gateways connect to the internet or other networks.

Day 1: The Big Picture (Architecture + Theory)

Today's goal: understand what each tool is, why it exists, and how they all connect, on AWS and Azure. No commands today. Only concepts. Hands-on starts on later days.

1. The problem DevOps solves

Old way: developers write code, then "throw it over the wall" to operations. Servers are set up by hand, so:

  • Every server is slightly different ("works on my machine").
  • Releases are slow, manual and risky.
  • Nobody can easily recreate a server that broke.

DevOps = automate everything between "code written" and "code running for users", and make it repeatable.

Read it from top to bottom:

  1. A developer pushes code to Git.
  2. CI/CD automatically builds and tests it, packages it as a Docker image, and stores it in a registry.
  3. Kubernetes pulls the image and runs it as containers, keeping the right number alive.
  4. All of this runs on cloud infrastructure, which Terraform created from code.

3.2 Infrastructure as Code: Terraform

What: You write the infrastructure you want in text files. Terraform builds it.

Why: Clicking in a console is slow and cannot be repeated or reviewed. Code can be stored in Git, reviewed, and re-run to build an identical environment.

How it works

 main.tf (what you WANT)
        │
        ▼
 terraform plan ──► compares WANT with STATE (what Terraform believes exists)
        │              and with the REAL cloud
        ▼
 terraform apply ──► calls AWS/Azure APIs through a PROVIDER to make reality match
        │
        ▼
 terraform.tfstate (updated record of what exists)

Key words:

  • Declarative: you say what you want ("3 servers"), not how to create them. Terraform works out the steps.
  • Provider: a plugin that talks to a platform (AWS, Azure, Kubernetes...).
  • State: Terraform's memory. In teams it is stored remotely (AWS S3 + DynamoDB lock, or Azure Blob) so two people do not change things at once.
  • Drift: someone changes something by hand, so reality no longer matches code. plan shows the difference.
  • Module: a reusable package of Terraform code.

AWS/Azure: same Terraform, different provider (aws or azurerm). Cloud-native alternatives: AWS CloudFormation, Azure Bicep.

3.3 Containers: Docker

What: A container packages your app with everything it needs (libraries, runtime) into one unit that runs the same everywhere.

Why: Fixes "works on my machine". Starts in seconds. Uses less than a virtual machine.

3.4 Orchestration: Kubernetes

What: A system that runs and manages many containers across many machines.

Why: One container is easy. Hundreds are not. Who restarts a crashed one? Who adds more when traffic grows? Who rolls out a new version without downtime? Kubernetes does.

Architecture

│  etcd         = database holding the desired state                     │
│  Scheduler    = decides which node runs each pod                       │
│  Controllers  = keep watching and fixing differences                   │

The core idea is the reconciliation loop: you declare "I want 3 copies of this app" → Kubernetes keeps comparing desired vs actual → if one dies, it starts another.

Key objects:

  • Pod: smallest unit, one or more containers together.
  • Deployment: "keep N pods of this version running"; handles rolling updates.
  • Service: a stable address in front of changing pods.
  • Ingress: routes outside web traffic to Services.
  • ConfigMap / Secret: configuration and sensitive values kept outside the image.
  • Namespace: a logical partition of the cluster.

AWS: EKS runs the control plane for you. Azure: AKS does the same. You manage worker nodes and workloads.

3.5 CI/CD

What: Automatic pipeline triggered by each code change.

  • CI (Continuous Integration): merge small changes often; every change is built and tested automatically.
  • Continuous Delivery: every passing build is ready to deploy; a human clicks to release.
  • Continuous Deployment: every passing build goes to production automatically.

Why: Finds bugs minutes after they are written, and makes releases boring and safe.

 commit → build → unit tests → security scan → package image → deploy to test → approve → deploy to prod
                  └────────── if any step fails, the pipeline stops ──────────┘

Key words: pipeline (the whole flow), stage/job (a step), runner/agent (the machine that executes jobs), artifact (a file produced by a job), environment (dev/test/prod).

Tools: GitLab CI/CD, Jenkins (you use both), GitHub Actions, Azure DevOps, AWS CodePipeline.

3.6 Scripting (bash / Python)

What: Small programs that automate repetitive tasks.

Why: Anything you do twice should be a script. Pipelines, servers and cloud CLIs are all driven by scripts.

  • Bash: best for gluing Linux commands together.
  • Python: better for logic, APIs, JSON, bigger tools.
  • Idempotent: running it twice gives the same result and does no harm. Aim for this.
  • Cloud CLIs (aws, az) are used inside scripts and pipelines.

5. How a change travels end to end

  1. Developer fixes a bug and pushes to GitLab.
  2. Pipeline runs tests, builds myapp:1.4.3, pushes it to ECR/ACR.
  3. Pipeline updates the Kubernetes Deployment to use 1.4.3.
  4. Kubernetes starts new pods, waits until they are healthy, then removes old ones (rolling update). Users see no downtime.
  5. If something is wrong, roll back to 1.4.2 with one command.
  6. If the cloud setup must change (e.g. bigger database), you change the Terraform code, review it in Git, and apply it.
