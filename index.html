10. Practical Hands-on Lab of the Day

Lab 2: Read-only Kubernetes troubleshooting assistant

Problem: A pod is in CrashLoopBackOff and you must read events, logs and describe output to find the cause.

Architecture: kubectl (read-only) → collect describe/events/logs → redact → LLM → plain-language cause + suggested fix → human decides.

Tools: kubectl, a read-only ServiceAccount, Python 3, an LLM API key in a vault.

Steps

  1. Create a read-only role: 
    kubectl create serviceaccount ai-triage -n demo
kubectl create role ai-triage-ro -n demo --verb=get,list --resource=pods,pods/log,events
kubectl create rolebinding ai-triage-ro -n demo --role=ai-triage-ro --serviceaccount=demo:ai-triage
  2. Collect context: 
    POD=$1; NS=demo
{ kubectl -n $NS describe pod $POD | tail -n 60
  kubectl -n $NS get events --field-selector involvedObject.name=$POD | tail -n 20
  kubectl -n $NS logs $POD --previous --tail=100; } > /tmp/ctx.txt
  3. Redact and send to the LLM (as in Lab 1): ask for "root cause, evidence lines, one fix, say unsure if unclear".
  4. Print the answer. Do not let the script run kubectl apply/delete.

Expected output: "OOMKilled: container limit 256Mi; evidence: Reason: OOMKilled; fix: raise memory limit or fix leak."

Security: read-only RBAC, namespace-scoped, redact env vars and tokens, never send Secrets, log every request.

Business value: faster first diagnosis for on-call; step toward approved auto-remediation.

10. Practical Hands-on Lab of the Day
Lab 1: AI analysis of Jenkins pipeline failures (read-only)

Problem: Developers spend time reading long Jenkins console logs to find why a build failed.

Architecture

Jenkins job fails → post-build step grabs last 300 log lines
        → script sends log to an LLM API → summary + likely cause
        → posted as a comment / Slack message (no write access to Jenkins/infra)

Tools: Jenkins, Python 3, an LLM API key (stored in Jenkins credentials / vault), requests.

Steps

  1. In Jenkins, add a credential LLM_API_KEY (secret text).
  2. Add to your Jenkinsfile:
post {
  failure {
    withCredentials([string(credentialsId: 'LLM_API_KEY', variable: 'LLM_API_KEY')]) {
      sh '''
        tail -n 300 "$WORKSPACE/build.log" > /tmp/tail.log || true
        python3 ai_triage.py /tmp/tail.log
      '''
    }
  }
}

(Make the build write to build.log, e.g. tee build.log, or fetch via currentBuild.rawBuild.getLog(300) in a shared library.)

  1. ai_triage.py (outline, adjust endpoint/model to your provider's docs):
import os, re, sys, requests
log = open(sys.argv[1]).read()
# redact obvious secrets before sending
log = re.sub(r'(?i)(password|token|secret|key)\s*[=:]\s*\S+', r'\1=<redacted>', log)
prompt = ("You are a CI triage assistant. Given this Jenkins log tail, "
          "give: 1) most likely root cause, 2) the exact failing step, "
          "3) one suggested fix. Say 'unsure' if not clear.\n\n" + log)
r = requests.post(os.environ["LLM_URL"],
    headers={"x-api-key": os.environ["LLM_API_KEY"]},
    json={"model": os.environ["LLM_MODEL"], "max_tokens": 500,
          "messages": [{"role": "user", "content": prompt}]}, timeout=60)
print(r.json())
  1. Send the printed summary to Slack/MR comment with a webhook.

Expected output: a 5-line message such as "Cause: docker pull timed out at registry; step: Build image; fix: retry / check registry network."

Security

  • Redact secrets before sending; never send full logs with credentials.
  • Read-only: the AI suggests, humans act.
  • Check your data-handling policy: logs leave your network.
  • Rate-limit and cap log size.

Business use: Lower time-to-diagnose for failed builds; a good first step before agentic remediation.

h) Beginner lesson of the day: what are EPS and the P/E ratio?

EPS (earnings per share) is the company's profit divided by the number of shares. If a company earns ₹1,000 crore and has 100 crore shares, EPS is ₹10. It tells you how much profit belongs to one share.

P/E (price-to-earnings ratio) is the share price divided by EPS. If the price is ₹200 and EPS is ₹10, P/E is 20. In plain words, you pay ₹20 for every ₹1 of yearly profit. A higher P/E means investors expect faster growth (or the stock is expensive); a lower P/E means slower growth (or the stock is out of favour).

How to use it: a P/E number means little alone. Compare it with (1) the same company's own past P/E, and (2) similar companies in the same sector: IT with IT, banks with banks. Banks are often judged with other measures too, such as price to book value.

Limits: if a company makes a loss, EPS is negative and P/E has no meaning (the case for Tata Motors PV this quarter). One-time gains can make P/E look low. P/E uses past profit, but share prices move on future expectations.

Try it today: on screener.in, open SBI and ITC, write down each P/E, and compare with the sector average shown there. Then write one line: "cheap or expensive versus peers, and why might that be?"

Daily lesson, 19 Nov 2026

Seven short blocks, one per tool, then a deep dive and an AI Pro section. Each block has four parts: what it is, why it matters, how it works, and how to use AI with it. Facts are from long-standing official documentation; open the links to confirm details.

AWS: accounts, regions, AZs, Organizations

What it is: An AWS account is the basic container for your resources and bills. A Region is a geographic area (for example Mumbai, ap-south-1). An Availability Zone (AZ) is one or more separate data centers inside a Region. AWS Organizations groups many accounts under one management account.

Why it matters: Accounts are the strongest isolation boundary (security and cost). Spreading across AZs keeps your app running if one data center fails.

How it works:

Organization (management account)
 ├─ OU: prod  ── account: app-prod
 └─ OU: dev   ── account: app-dev
Region ap-south-1
 ├─ AZ a   ├─ AZ b   └─ AZ c   (separate failure domains)

How to use AI with it: Prompt: "Suggest an AWS Organizations layout with OUs for prod, dev and security for a 10-person team, and explain why each account exists." Safety tip: never paste access keys or account IDs of production into a chat; ask for a design, then apply it yourself.

Docs: What is AWS Organizations · Regions and Availability Zones

Azure: tenants, subscriptions, resource groups

What it is: A tenant is your organization's identity space (Microsoft Entra ID). A subscription is a billing and access boundary inside it. A resource group is a folder for related resources (VMs, databases) that share a life cycle. Management groups sit above subscriptions.

Why it matters: You apply policy, access (RBAC) and budgets at these levels, so a good layout saves you from messy permissions later.

How it works:

Tenant (Entra ID)
 └─ Management group
     └─ Subscription
         └─ Resource group
             └─ Resource (VM, storage, ...)

How to use AI with it: Prompt: "Compare an Azure subscription-per-environment layout with a single subscription and resource groups. List pros and cons for a small team." Safety tip: AI may mix up AWS and Azure terms (an AWS account is closest to an Azure subscription); check against the docs.

Docs: Organize Azure resources

Docker: containers vs VMs

What it is: A container packages an app and its libraries and runs as an isolated process on the host's kernel. A virtual machine runs a full guest operating system on a hypervisor.

Why it matters: Containers start in seconds, use less memory and run the same on a laptop and a server. The trade-off is weaker isolation than a VM because the kernel is shared.

How it works:

VM:         App | Guest OS | Hypervisor | Hardware
Container:  App + libs | Container runtime | Host OS kernel | Hardware

How to use AI with it: Prompt: "Explain in five lines why a container is not a VM, then give me a quiz of three questions." Safety tip: do not run commands from an AI answer with --privileged or by mounting the Docker socket unless you understand why.

Docs: Docker overview

Kubernetes: cluster architecture

What it is: A cluster has a control plane (API server, etcd, scheduler, controller manager) that decides what should run, and worker nodes (kubelet, container runtime, kube-proxy) that run your Pods.

Why it matters: Every kubectl command, deployment and failure ends up in these parts. Knowing them makes troubleshooting faster.

How it works:

kubectl ──> API server ──> etcd (state)
              │  scheduler picks a node
              ▼
        Node: kubelet ──> container runtime ──> Pods

How to use AI with it: Prompt: "Walk through what happens, step by step, when I run kubectl apply -f deploy.yaml." Safety tip: give AI tools read-only cluster access first; never share kubeconfig files or Secrets.

Docs: Cluster architecture

Terraform: declarative IaC, init, plan, apply

What it is: Infrastructure as Code: you write what you want (a network, a VM) in files, and Terraform works out the steps to get there. This is declarative, unlike a script of commands.

Why it matters: Changes are reviewed, repeatable and stored in Git. plan shows the effect before anything changes.

How it works:

terraform init   -> download providers
terraform plan   -> show what will change
terraform apply  -> make the change, record it in state

Deep dive of the day: Kubernetes cluster architecture

The idea. Kubernetes keeps your declared wish ("run 3 copies of this app") true. You write the wish as objects; Kubernetes keeps comparing the desired state with the actual state and fixes any difference. This loop is called reconciliation, and nearly everything in the cluster works this way.

The architecture. A cluster has a control plane (the brain) and worker nodes (the muscle).

        kubectl / CI / Argo CD
                 |  (HTTPS, authenticated)
                 v
 +-------------- CONTROL PLANE ---------------+
 |  kube-apiserver  <-->  etcd (state DB)      |
 |      ^    ^                                 |
 |      |    +-- kube-scheduler (picks a node) |
 |      +------- controller-manager (loops)   |
 +---------------------------------------------+
        | watch / report
 +------v-------+  +-------------+  +-------------+
 | Node 1       |  | Node 2      |  | Node 3      |
 | kubelet      |  | kubelet     |  | kubelet     |
 | kube-proxy   |  | kube-proxy  |  | kube-proxy  |
 | runtime      |  | runtime     |  | runtime     |
 | [Pod] [Pod]  |  | [Pod]       |  | [Pod] [Pod] |
 +--------------+  +-------------+  +-------------+

The API server is the only front door; the other parts talk to it, not to each other. etcd stores all cluster state, so back it up. The scheduler only decides which node a new Pod runs on (using resource requests, taints, affinity). Controllers (Deployment, ReplicaSet, Node and more) run the reconcile loops. On each node the kubelet starts containers through a container runtime (such as containerd) and reports health; kube-proxy (or an eBPF network plugin) makes Services reachable.

Real-world example. You run kubectl apply -f deploy.yaml with replicas: 3. The API server validates the Deployment and stores it in etcd. The Deployment controller creates a ReplicaSet, which creates 3 Pod objects with no node. The scheduler assigns each Pod to a node. Each node's kubelet sees "a Pod is assigned to me" and starts it. If a node dies, the node controller marks its Pods lost, the ReplicaSet creates new Pods, and the scheduler places them on healthy nodes. In managed services such as EKS or AKS the provider runs the control plane; you manage the worker nodes.

Common mistakes. (1) One control-plane node in production (use 3 for etcd quorum, or a managed service). (2) No etcd backups on self-managed clusters. (3) Pods with no resource requests, so one noisy Pod can starve others. (4) Giving everyone cluster-admin. (5) Thinking the scheduler restarts containers; that is the kubelet's job. (6) Running retired components: ingress-nginx was retired in March 2026 and a recent CVE got no fix (see today's log), so plan a maintained ingress or Gateway API controller.

Mini exercise (15 min). Install kind or minikube. Run kubectl get nodes, then kubectl get pods -n kube-system and find the API server, etcd, scheduler and controller-manager Pods. Create a Deployment (kubectl create deployment web --image=nginx --replicas=3), then kubectl get pods -o wide to see which node each Pod got. Delete one Pod and watch a new one appear. Run kubectl describe pod <name> and read the Events: "Scheduled" (scheduler), then "Pulled" and "Started" (kubelet). Docs: Cluster architecture.

AI Pro (professional level): transformer attention and context windows

Concepts. A transformer turns text into tokens, maps each token to a vector, and passes them through layers. In each layer, self-attention lets every token compute a weighted mix of other tokens' information. Each token produces a query (Q), key (K) and value (V); the attention weights are softmax(QKT/√d) and the output is those weights times V. Multi-head attention runs several of these in parallel so the model can track different relations (syntax, references, code scope). Chat models are decoder-only with a causal mask, so a token sees only earlier tokens. Primary source: Attention Is All You Need.

Why context windows matter for design. Cost and latency grow with the number of tokens: naive attention work grows roughly with the square of sequence length (implementations use optimisations), and the KV cache (stored K and V of earlier tokens) takes GPU memory in proportion to length. Providers bill input and output tokens, usually at different rates. A large window does not mean equal attention everywhere: models can miss details buried in long inputs, so test this rather than assume it.

request = [ system | tools | docs / retrieved chunks | history | user question ]
            ^ stable prefix (cacheable)             ^ changes every call
budget:  input_tokens + max_output_tokens <= context_window
policy:  trim history -> summarise old turns -> retrieve only top-k chunks

Design pattern. Put stable content (instructions, tool schemas, reference docs) first and volatile content last, so a reusable prefix can be cached by the provider (the next AI Pro topic). Keep a token budget per request and reserve space for the answer. Prefer retrieving a few relevant chunks over pasting whole repositories.

Trade-offs. Long context: simpler pipeline, but higher cost and latency and a risk of distraction. Retrieval: cheaper and more focused, but it can miss facts if chunking or search is poor. Summarising history: saves tokens, but loses detail and can lock in earlier errors.

Failure modes. Silent truncation when you exceed the limit; stale or conflicting facts in a long context; the model following instructions hidden in retrieved text (prompt injection); cost spikes when an agent loop keeps appending tool output to the history.

Sketch (token budget guard, Python):

MAX_CTX, RESERVE = 200_000, 4_000   # example numbers; use your model's real limits
def build(messages, count_tokens):
    budget = MAX_CTX - RESERVE
    kept, used = [], 0
    for m in reversed(messages):          # keep newest turns first
        t = count_tokens(m)
        if used + t > budget:
            break
        kept.append(m); used += t
    return list(reversed(kept))           # system prompt is added separately

Evaluation, security, cost. Evaluate with a golden set that places the key fact at the start, middle and end of the context and checks the answer. Log input and output tokens per request and alert on p95 growth. Treat anything retrieved or returned by a tool as untrusted data; it must never change tool permissions. Measure cost before choosing a bigger window.

1. Theory: what, why, how

  • What: a virtual private network you define in software. AWS calls it a VPC, Azure a Virtual Network (VNet). You choose an IP range (CIDR, e.g. 10.0.0.0/16) and split it into subnets.

1. The problem DevOps solves

Old way: developers write code, then "throw it over the wall" to operations. Servers are set up by hand, so:

  • Every server is slightly different ("works on my machine").
  • Releases are slow, manual and risky.
  • Nobody can easily recreate a server that broke.

3.5 CI/CD

What: Automatic pipeline triggered by each code change.

  • CI (Continuous Integration): merge small changes often; every change is built and tested automatically.
  • Continuous Delivery: every passing build is ready to deploy; a human clicks to release.
  • Continuous Deployment: every passing build goes to production automatically.

Why: Finds bugs minutes after they are written, and makes releases boring and safe.

 commit → build → unit tests → security scan → package image → deploy to test → approve → deploy to prod
                  └────────── if any step fails, the pipeline stops ──────────┘

Key words: pipeline (the whole flow), stage/job (a step), runner/agent (the machine that executes jobs), artifact (a file produced by a job), environment (dev/test/prod).

Tools: GitLab CI/CD, Jenkins (you use both), GitHub Actions, Azure DevOps, AWS CodePipeline.

3.6 Scripting (bash / Python)

What: Small programs that automate repetitive tasks.

Why: Anything you do twice should be a script. Pipelines, servers and cloud CLIs are all driven by scripts.

  • Bash: best for gluing Linux commands together.
  • Python: better for logic, APIs, JSON, bigger tools.
  • Idempotent: running it twice gives the same result and does no harm. Aim for this.
  • Cloud CLIs (aws, az) are used inside scripts and pipelines.
